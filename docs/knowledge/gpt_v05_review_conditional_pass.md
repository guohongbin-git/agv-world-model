## 二、遗留分歧 P0-2：接受命题定位，但否决当前“上界”定义

### 裁决：原则接受，验收方式必须改

你对 Paper I 的理解是正确的：

> 物理动作不可回滚，数据库可以事务化。因此系统必须管理物理事实与数字提交之间不可避免的不一致窗口，而不是假装窗口不存在。

这个窗口**不是架构缺陷本身**。

真正的架构缺陷是：窗口内发生崩溃、网络分区或证据过期时，系统丢失了事实、错误提交，或者永久卡住却无法发现。

但目前这条：

`max(t_commit − t_event_settle)`

只能得到**已经成功提交的样本中的最大观测延迟**，不能叫“非原子窗口上界”。

原因是：一笔已经发生物理动作、但永远没有提交的事务，不会进入这个最大值的计算。恰恰是最危险的长尾被排除了。

建议拆成三类验收指标：

| 指标 | 定义 | 用途 |
|---|---|---|
| 已闭合窗口 | 物理稳定到持久化提交的时间，报告 p50/p95/p99/max | 测量正常闭合成本 |
| 未闭合窗口 | 已确认物理变化、但事务仍待决的持续时间及未决数量 | 识别长时间卡住的事务 |
| 故障恢复 | 故障注入到恢复账实一致的时间、成功率及超时数量 | 验证恢复机制 |

还要明确两个不同目标：

**Safety：** 不能因为恢复失败，就把没有证据支持的物理动作提交为成功。

**Liveness：** 在明确的故障模型和恢复假设下，未决事务最终能够关闭或进入人工介入状态。

对于无限期网络分区或永久设备失联，不能承诺一个无条件的有限闭合时间上界。能保证的是维持安全的未决状态、持续监控、超时升级和可恢复性。

因此我批准的修订表述是：

> 非原子窗口是 Paper I 的核心研究对象，而非需要消除的设计缺陷。项目测量已闭合窗口的时延分布、监控未闭合窗口的持续时间，并在声明的故障与恢复假设下验证恢复结果。不将样本最大值宣称为理论上界。

同时把风险等级从 `low` 调整为 **high（恢复测试通过前）**。

## 三、五项必须修改的冻结条件

以下是签字前必须完成的条件。不是建议项。

### C1｜时间模型：必须分离真值发生时间与可观测时间

BLOCKER · P0 前

目前三元组的最大问题是 `t_event`。

物理事件真实发生的时刻，往往只有仿真真值知道。摄像头只能在某个采样时刻观测到物理状态，并估计事件发生时间。

如果在每条运行时证据帧中放入精确的 `t_event`，这个字段可能直接成为真值泄漏通道。

建议采用两个独立时间契约。

**运行时证据：**

```text
run_id / sim_epoch / operation_id
source_id / source_sequence

t_capture      观测采样时间
t_ingest       事件进入融合层时间
t_decide       证据裁决时间

estimated_event_time   可选，有误差/不确定性
```

**独立评分器：**

```text
truth_event_time
truth_settle_time
truth_state
durable_commit_time
```

物理稳定窗由观测时间序列和观测有效期来判断；真实的物理稳定发生时间仅用于离线评分。

对受控、同一时钟域的消息要求：

\[
t_{\text{capture}}\leq t_{\text{ingest}}\leq t_{\text{decide}}
\]

跨时钟域则需要明确同步误差，不能直接用数值单调性断言。

另外，“wall clock 禁止进入任何判据/日志排序”应改为：

- 仿真业务语义与确定性事件调度采用 `sim_t`。
- 实际运行监控记录 wall time，用于 watchdog、资源性能和运行故障排查。
- 两者不能混用来计算同一指标。

MuJoCo 官方将 `mjData.time` 定义为物理状态中的仿真时间，并不能据此推断真实进程耗时或外部消息延迟。

**验收：** 构造延迟、乱序、重复、过期和跨重启消息测试，确保运行时门控不依赖评分器独有的事件真值时间。

### C2｜独立评分器：必须证明 Oracle 独立，而不只是进程独立

BLOCKER · P0 前

两个进程如果复用同一个托盘归属推导函数，仍然可能一起得出错误结论。

P0 需要定义独立评分器的最小契约：

- 读取独立导出的物理真值轨迹，以及持久化账本快照或事件日志。
- 不调用被测系统的业务判定函数来推导实际托盘归属。
- 按 `pallet_id + location + custody + operation_id` 检查归属与事务。
- 使用一致的快照边界，区别短暂未决状态和持久账实错误。
- 记录输入文件哈希、core 版本、规则版本和 run_id。

P0 还缺少上一轮要求的负向验收。至少补齐：未装车伪造成功、装错卡车、提交前崩溃、提交后 ACK 丢失、重复事件、未结清货物时离场。

**验收：** 主动向被测系统注入错误提交和错误托盘归属，独立评分器必须能识别。再人为给出一个正确但尚未闭合的事务，评分器必须识别为待恢复而不是已完成或丢失。

否则“独立评分器 PASS”仍然有伪验收风险。

### C3｜Pareto：必须区分外部噪声条件与可控制策略

BLOCKER · P1 前

v0.5 这里存在一个方法论错误：

**漏检率、误检率和传感器延迟是实验环境条件，不是策略优化变量。**

不能把不同噪声条件下的结果混在一起画 Pareto 前沿，然后找到一个表现好的点就宣称系统达标。

低噪声条件天然可能支配高噪声条件，但系统不能通过“选择一个噪声更小的真实世界”来完成优化。

正确设计是：

- 固定噪声条件；
- 在这个条件下调整可控策略，例如重观测次数、融合阈值、证据等待预算；
- 对不同策略计算 unsafe / FRR / throughput；
- 按噪声条件分别形成 Pareto 前沿，再比较鲁棒性。

而且签字门槛不能只要求“存在一个满足 unsafe=0 且 FRR≤5% 的非支配点”。

因为这仍然允许系统以极低吞吐甚至长期挂起任务来换取漂亮结果。

建议恢复为：

| 指标 | P1 验收原则 |
|---|---|
| Unsafe commit | 样本中 0 次，另报暴露次数和置信上界 |
| False reject | ≤5%，含截止时间内无法闭合的正确事务 |
| Throughput loss | 保留预先声明的上限，建议仍以原定 ≤10% 为目标 |
| Recovery | 报超时率及 p95/p99，而不只报成功案例 |
| Robustness | 必须在预先指定的压力点测试，而不是事后从网格中挑最优点 |

如果 10% 吞吐目标确实无法达到，可以给出经过论证的新约束，但不能简单删除成本约束后宣布 PASS。

再强调：**不同故障配置下各出现 0 次 unsafe，不意味着风险为零。** 如果某配置只有 30 次独立暴露机会，0/30 对真实失败概率的单侧 95% 上界仍约为 9.5%。

### C4｜两级感知：禁止使用带有真值身份的 observed 通道

BLOCKER · P1 前

v0.5 的这句话仍不足够：

> L2a 只从 observed 口径取数 + 自有噪声变换，信息源独立性由构造保证。

我不接受“由构造保证”，除非明确构造是什么。

假设 observed 已经携带准确的 MuJoCo 对象 ID、精确托盘姿态或真实承托状态，只在外面加上 20% 漏检，仍然是带真值身份的传感器。

而且 Camera 和 LiDAR 如果共享同一份完美定位结果，即使各自独立加随机噪声，也可能存在未覆盖的共同原因故障。

需要补三项：

1. L2a 只能输出其观测模型能够产生的量，不能直接输出真实 `pallet_id` 或接触稳定结论。
2. 加入身份混淆、连续遮挡、相关偏差和消息重放测试，而不只是三个独立噪声百分比。
3. 对比无摄像头、增加摄像头、摄像头受干扰三种实验组，证明新通道确实提供增量证据价值。

现有的证据能力矩阵可以保留，但 `LiDAR σ=3mm` 等没有标定来源的数值必须标记为合成假设。

另外，接触/力仍然处于理想观测 regime。如果它是门控的决定性来源，那么 P1 即使增加了有噪声的摄像头，也可能没有真正测试关键证据失效。

**验收：** 在接触/力证据不完整、摄像头被欺骗以及多源共同偏差下，验证系统是否正确拒绝、等待或恢复，而不只是验证无噪声主传感器仍然可靠。

### C5｜契约回归门：不能把历史数字冻结成真理

BLOCKER · 首次 core 发布前

我赞同把 1200-run 消融纳入 CI，但反对：

> 数字漂移即 FAIL。

例如，改进 B1 后 unsafe 从 4.8% 降为 2%，按照当前规则反而可能失败。

这属于**结果快照回归**，不是语义契约验证。

建议三层门禁：

| 门禁 | 判定方式 |
|---|---|
| 契约门 | 不变量、非法状态转移、重复提交、证据过期、异常恢复不得违反 |
| 确定性门 | 固定版本与环境下，同 seed 的事件序列/裁决结果可重现 |
| 统计门 | unsafe、FRR、恢复、吞吐相对参考基线不得发生未经批准的实质性退化 |

1200-run 原始历史基准应冻结为可追溯的研究数据集，新的实现按明确判定规则比较，而不是强制保持历史 B0/B1/B2/B3 数字完全相同。

同时 §6 的封装方案还需要改。

`__all__` 只能控制 Python 模块的公开名称及通配导入行为，不是禁止外部项目访问内部模块的隔离机制。

尤其不能把 `ledger 事务` 直接当成公共能力暴露给 `dc-twin`，以免外部绕开证据门控。

最小签字条件是：

- 对外暴露经过授权的提交命令和只读账本投影，而不是任意账本修改能力。
- 使用依赖边界检查、契约测试和正式 wheel 安装测试。
- 独立评分器只依赖公共数据格式，不应为了评分而导入被测系统的事务实现。
- 合成仿真和渲染可选依赖不得污染独立的证据契约包。

## 四、另外三处必须写入工程记录，但不阻断架构方向

这三处可以纳入阶段实现验收，不必再触发一次完整架构重审。

**1. P0 时间估计仍然明显乐观。** 1–2 天同时完成新增 load 腿、卡车装卸、账本变更、需求引擎和独立评分，除非大量代码已经存在，否则不能直接当作可信交付周期。必须先实现接口与负向测试，再做时间承诺。

**2. P2 矩阵是 540 runs。** `3×3×1` 摸底需要标明三个轴以及固定的其他参数；如果其中一个 3 代表月台数量，就与只提供 4/6 两种月台配置冲突。另外 10 车配置必须有相应机器人资产和调度能力，不应只把 8 车参数改成 10。P2 正式验收还需可复现的 manifest 与统计报告。

**3. P3 仍然缺少可追溯验收。** Blender + 检测器既然只是演示，就不能拿它证明 P1 感知性能。60–90 秒成片必须关联 run_id、物理状态、事件流和 EvidenceVerdict。否则只是视觉交付，不是架构证据。

### 最后裁决

上一轮 v0.4 的根本问题是**场景优先于执行证据**。这一点 v0.5 已经纠正，不需要再次推翻总体架构。

本轮剩下的问题集中在证据协议的可信性和实验方法，而不是 DC 场景本身。

**P0-2 分歧正式裁决：接受项目方的命题定位；非原子窗口是研究对象，不是要求消除的缺陷。但未决窗口可监控、异常可恢复以及风险不被错误提交掩盖，必须作为强制验收。**

建议下一版直接定为 **v0.5.1 冻结修订版**，只修改上述五项，不再扩展场景功能。五项条件落实并能与测试规范对应后，可以冻结蓝图并进入 P0。

本轮无需再进行一次大规模架构推倒重来。

## 三、五项必须修改的冻结条件

以下是签字前必须完成的条件。不是建议项。

### C1｜时间模型：必须分离真值发生时间与可观测时间

BLOCKER · P0 前

目前三元组的最大问题是 `t_event`。

物理事件真实发生的时刻，往往只有仿真真值知道。摄像头只能在某个采样时刻观测到物理状态，并估计事件发生时间。

如果在每条运行时证据帧中放入精确的 `t_event`，这个字段可能直接成为真值泄漏通道。

建议采用两个独立时间契约。

**运行时证据：**

```text
run_id / sim_epoch / operation_id
source_id / source_sequence

t_capture      观测采样时间
t_ingest       事件进入融合层时间
t_decide       证据裁决时间

estimated_event_time   可选，有误差/不确定性
```

**独立评分器：**

```text
truth_event_time
truth_settle_time
truth_state
durable_commit_time
```

物理稳定窗由观测时间序列和观测有效期来判断；真实的物理稳定发生时间仅用于离线评分。

对受控、同一时钟域的消息要求：

\[
t_{\text{capture}}\leq t_{\text{ingest}}\leq t_{\text{decide}}
\]

跨时钟域则需要明确同步误差，不能直接用数值单调性断言。

另外，“wall clock 禁止进入任何判据/日志排序”应改为：

- 仿真业务语义与确定性事件调度采用 `sim_t`。
- 实际运行监控记录 wall time，用于 watchdog、资源性能和运行故障排查。
- 两者不能混用来计算同一指标。

MuJoCo 官方将 `mjData.time` 定义为物理状态中的仿真时间，并不能据此推断真实进程耗时或外部消息延迟。

**验收：** 构造延迟、乱序、重复、过期和跨重启消息测试，确保运行时门控不依赖评分器独有的事件真值时间。

### C2｜独立评分器：必须证明 Oracle 独立，而不只是进程独立

BLOCKER · P0 前

两个进程如果复用同一个托盘归属推导函数，仍然可能一起得出错误结论。

P0 需要定义独立评分器的最小契约：

- 读取独立导出的物理真值轨迹，以及持久化账本快照或事件日志。
- 不调用被测系统的业务判定函数来推导实际托盘归属。
- 按 `pallet_id + location + custody + operation_id` 检查归属与事务。
- 使用一致的快照边界，区别短暂未决状态和持久账实错误。
- 记录输入文件哈希、core 版本、规则版本和 run_id。

P0 还缺少上一轮要求的负向验收。至少补齐：未装车伪造成功、装错卡车、提交前崩溃、提交后 ACK 丢失、重复事件、未结清货物时离场。

**验收：** 主动向被测系统注入错误提交和错误托盘归属，独立评分器必须能识别。再人为给出一个正确但尚未闭合的事务，评分器必须识别为待恢复而不是已完成或丢失。

否则“独立评分器 PASS”仍然有伪验收风险。

### C3｜Pareto：必须区分外部噪声条件与可控制策略

BLOCKER · P1 前

v0.5 这里存在一个方法论错误：

**漏检率、误检率和传感器延迟是实验环境条件，不是策略优化变量。**

不能把不同噪声条件下的结果混在一起画 Pareto 前沿，然后找到一个表现好的点就宣称系统达标。

低噪声条件天然可能支配高噪声条件，但系统不能通过“选择一个噪声更小的真实世界”来完成优化。

正确设计是：

- 固定噪声条件；
- 在这个条件下调整可控策略，例如重观测次数、融合阈值、证据等待预算；
- 对不同策略计算 unsafe / FRR / throughput；
- 按噪声条件分别形成 Pareto 前沿，再比较鲁棒性。

而且签字门槛不能只要求“存在一个满足 unsafe=0 且 FRR≤5% 的非支配点”。

因为这仍然允许系统以极低吞吐甚至长期挂起任务来换取漂亮结果。

建议恢复为：

| 指标 | P1 验收原则 |
|---|---|
| Unsafe commit | 样本中 0 次，另报暴露次数和置信上界 |
| False reject | ≤5%，含截止时间内无法闭合的正确事务 |
| Throughput loss | 保留预先声明的上限，建议仍以原定 ≤10% 为目标 |
| Recovery | 报超时率及 p95/p99，而不只报成功案例 |
| Robustness | 必须在预先指定的压力点测试，而不是事后从网格中挑最优点 |

如果 10% 吞吐目标确实无法达到，可以给出经过论证的新约束，但不能简单删除成本约束后宣布 PASS。

再强调：**不同故障配置下各出现 0 次 unsafe，不意味着风险为零。** 如果某配置只有 30 次独立暴露机会，0/30 对真实失败概率的单侧 95% 上界仍约为 9.5%。

### C4｜两级感知：禁止使用带有真值身份的 observed 通道

BLOCKER · P1 前

v0.5 的这句话仍不足够：

> L2a 只从 observed 口径取数 + 自有噪声变换，信息源独立性由构造保证。

我不接受“由构造保证”，除非明确构造是什么。

假设 observed 已经携带准确的 MuJoCo 对象 ID、精确托盘姿态或真实承托状态，只在外面加上 20% 漏检，仍然是带真值身份的传感器。

而且 Camera 和 LiDAR 如果共享同一份完美定位结果，即使各自独立加随机噪声，也可能存在未覆盖的共同原因故障。

需要补三项：

1. L2a 只能输出其观测模型能够产生的量，不能直接输出真实 `pallet_id` 或接触稳定结论。
2. 加入身份混淆、连续遮挡、相关偏差和消息重放测试，而不只是三个独立噪声百分比。
3. 对比无摄像头、增加摄像头、摄像头受干扰三种实验组，证明新通道确实提供增量证据价值。

现有的证据能力矩阵可以保留，但 `LiDAR σ=3mm` 等没有标定来源的数值必须标记为合成假设。

另外，接触/力仍然处于理想观测 regime。如果它是门控的决定性来源，那么 P1 即使增加了有噪声的摄像头，也可能没有真正测试关键证据失效。

**验收：** 在接触/力证据不完整、摄像头被欺骗以及多源共同偏差下，验证系统是否正确拒绝、等待或恢复，而不只是验证无噪声主传感器仍然可靠。

### C5｜契约回归门：不能把历史数字冻结成真理

BLOCKER · 首次 core 发布前

我赞同把 1200-run 消融纳入 CI，但反对：

> 数字漂移即 FAIL。

例如，改进 B1 后 unsafe 从 4.8% 降为 2%，按照当前规则反而可能失败。

这属于**结果快照回归**，不是语义契约验证。

建议三层门禁：

| 门禁 | 判定方式 |
|---|---|
| 契约门 | 不变量、非法状态转移、重复提交、证据过期、异常恢复不得违反 |
| 确定性门 | 固定版本与环境下，同 seed 的事件序列/裁决结果可重现 |
| 统计门 | unsafe、FRR、恢复、吞吐相对参考基线不得发生未经批准的实质性退化 |

1200-run 原始历史基准应冻结为可追溯的研究数据集，新的实现按明确判定规则比较，而不是强制保持历史 B0/B1/B2/B3 数字完全相同。

同时 §6 的封装方案还需要改。

`__all__` 只能控制 Python 模块的公开名称及通配导入行为，不是禁止外部项目访问内部模块的隔离机制。

尤其不能把 `ledger 事务` 直接当成公共能力暴露给 `dc-twin`，以免外部绕开证据门控。

最小签字条件是：

- 对外暴露经过授权的提交命令和只读账本投影，而不是任意账本修改能力。
- 使用依赖边界检查、契约测试和正式 wheel 安装测试。
- 独立评分器只依赖公共数据格式，不应为了评分而导入被测系统的事务实现。
- 合成仿真和渲染可选依赖不得污染独立的证据契约包。

## 四、另外三处必须写入工程记录，但不阻断架构方向

这三处可以纳入阶段实现验收，不必再触发一次完整架构重审。

**1. P0 时间估计仍然明显乐观。** 1–2 天同时完成新增 load 腿、卡车装卸、账本变更、需求引擎和独立评分，除非大量代码已经存在，否则不能直接当作可信交付周期。必须先实现接口与负向测试，再做时间承诺。

**2. P2 矩阵是 540 runs。** `3×3×1` 摸底需要标明三个轴以及固定的其他参数；如果其中一个 3 代表月台数量，就与只提供 4/6 两种月台配置冲突。另外 10 车配置必须有相应机器人资产和调度能力，不应只把 8 车参数改成 10。P2 正式验收还需可复现的 manifest 与统计报告。

**3. P3 仍然缺少可追溯验收。** Blender + 检测器既然只是演示，就不能拿它证明 P1 感知性能。60–90 秒成片必须关联 run_id、物理状态、事件流和 EvidenceVerdict。否则只是视觉交付，不是架构证据。

### 最后裁决

上一轮 v0.4 的根本问题是**场景优先于执行证据**。这一点 v0.5 已经纠正，不需要再次推翻总体架构。

本轮剩下的问题集中在证据协议的可信性和实验方法，而不是 DC 场景本身。

**P0-2 分歧正式裁决：接受项目方的命题定位；非原子窗口是研究对象，不是要求消除的缺陷。但未决窗口可监控、异常可恢复以及风险不被错误提交掩盖，必须作为强制验收。**

建议下一版直接定为 **v0.5.1 冻结修订版**，只修改上述五项，不再扩展场景功能。五项条件落实并能与测试规范对应后，可以冻结蓝图并进入 P0。

本轮无需再进行一次大规模架构推倒重来。
