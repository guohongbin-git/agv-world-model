**最致命的问题不是技术不够复杂，而是把三个不同层次的成果混在一起：**

- **工程成果：** 已经构建了一个相对完整的多 AGV 物理仿真与故障执行系统。这部分有实在的工程工作量。

另外，**AGV World Model 这个名称也值得重新审视。** 目前描述更像 Physics-Grounded Execution Assurance（物理证据支撑的执行可信层），而不是拥有环境预测、在线状态估计和持续模型校准能力的完整 World Model。过度使用这个标签，会招来不必要的技术质疑。

## 二、技术护城河与可复制性

### 结论：机制组合有价值，基础思想缺乏独占性

我会把你的系统拆成三个部分来看：

| 技术组成 | 可复制难度 | 投资判断 |
|---|---|---|
| 物理证据门控 | 低至中 | 传感器融合、阈值和时间窗判定属于常见工程手段 |
| 原子事务与防重复提交 | 低至中 | 数据库事务、幂等、事件日志和恢复模式已有成熟实践 |
| 断链后的重新观测与账实对账 | 中至高 | 真正复杂的是跨设备、跨系统的异常状态识别与恢复 |

你真正可能有价值的是第三层，以及三层之间可形式化验证的执行契约，而不是“有证据才能提交”这句话。

### 1. 谁最容易复制？

  
    
    
      **KUKA 等机器人及调度厂商**

      最大商业威胁

      已有任务状态、机器人控制器、设备反馈、PLC 接口和工业客户。把证据校验嵌入现有任务结束条件，比引进外部独立平台更自然。KUKA.AMR Fleet 已覆盖异构车队、WMS/MES 集成、任务监控和故障诊断。
    
  
  
  
    
    
      **openTCS 生态及系统集成商**

      现有系统已经支持任务生命周期、失败状态以及外围设备执行反馈。特别值得注意的是，openTCS 7 的外围设备作业支持“必须成功完成”的依赖语义；外围操作失败可以触发关联运输单撤销。不能再把它描述成完全没有执行确认能力的系统。
    
  
  
  
    
    
      **极智嘉 等软硬件一体化厂商**

      已经把 WES、RMS、数据监控、仿真与 ERP/WMS/MES 集成作为完整产品提供。它们有能力把新的确认机制作为现有软件更新，而不是采购第三方模块。
    
  

### 2. 你的差异化究竟在哪里？

截至 2026 年，VDA 5050 已发布 3.0 版本，协议包含动作状态、重试以及失败报告等机制。**这并不等价于独立的物理证据核验和企业账本原子提交**，所以你仍有可切入的空白；但它证明行业早就在处理任务状态与异常，而不是一个完全无人涉足的问题。

更准确的技术定位应当是：

> 在异构机器人控制系统与企业业务账本之间，提供可审计的物理执行证据、提交裁决和异常恢复协议。

这个定位比“工业 WMS/MES 都没有事务-物理一致性层”更可信，也更经得起客户技术团队检验。

### 3. 专利、数据还是生态，哪个能防御？

| 防御方式 | 当前强度 | 未来潜力 |
|---|---|---|
| 算法/软件专利 | 弱 | 中低 |
| 合成故障仿真数据 | 弱 | 低 |
| 真实跨厂商故障与恢复数据 | 尚无 | 高 |
| 深度 OEM/PLC/WMS 集成 | 尚无 | 高 |
| 可复用的证据契约及认证测试体系 | 初具雏形 | 中高 |

广义的“检测物理状态，再允许提交”很难成为有力的排他性专利；具体证据时序、传感器仲裁、跨系统恢复协议可以尝试专利保护，但必须做现有技术检索和权利要求评估。

**最终判断：真正可能形成护城河的，不是门控算法，而是经过现场验证、设备无关且难以替换的执行证据与恢复体系。** 没有真实工业接口、现场故障数据和客户集成深度，当前护城河仍主要是工程积累。

## 三、市场与付费场景：最大问题是客户为什么不自己做

### 结论：有商业需求，但最可能的买家同时也是最可能的复制者

行业大市场并不小。Interact Analysis 在 2026 年 1 月预测，全球移动机器人市场收入将从 2024 年不足 50 亿美元增长到 2030 年约 140 亿美元。

但这个数字对你几乎没有直接估值意义。它包括机器人硬件与整体系统收入，不是“执行证据软件”的可服务市场。

### 1. 客户优先级与收费能力

以下价格是**建议测试的合同区间，不是已经验证的市场成交价格**，金额均为人民币。

| 客户类型 | 痛点和支付意愿 | 可测试价格 | 优先级 |
|---|---|---|---|
| AMR/AGV 厂商 | 设备误报完成、客户索赔、售后排障 | 30–150 万/年 OEM 框架授权 | 高 |
| WES/WCS 集成商 | 跨设备异常恢复、账实不同步 | 8–30 万/站点/年 | 最高 |
| 终端工厂/仓库 | 库存差异、停线、异常人工处置 | 8–30 万/站点/年 | 中高 |
| WMS 软件厂商 | 机器人任务状态可信度 | 联合项目或 OEM 授权 | 中 |
| 仿真软件厂商 | 故障注入、测试和验证 | 5–20 万/年工具许可 | 低 |

我认为**第一批客户应该是复杂项目的 WES/WCS 系统集成商，而不是终端工厂，也不是最大的 AMR 厂商。**

原因很直接：

大型 AMR 厂商有研发能力，倾向于自己实现。终端工厂通常不会为了物理证据门控单独引入一套核心软件；而集成商长期处于机器人系统与客户 WMS/MES 的交界处，最容易为两边责任不清、异常人工对账付出成本。

然而，集成商也可能选择自己开发。你必须证明购买比自研便宜，并且能降低项目交付与售后成本。

### 2. 你还没建立客户 ROI

假设某仓库每年有 100 万次货物移动任务，每次虚假完成平均造成 1000 元的排障、人工处理和业务损失。

  假设场景：虚假完成的年度经济损失
  
    
      
        虚假完成率 0.01%
        **10 万元/年**
        100 次 × 1000 元
      
    
    
      
        虚假完成率 0.1%
        **100 万元/年**
        1000 次 × 1000 元
      
    
  
  纯情景假设，不代表真实行业发生率或平均损失。

如果客户实际损失只有每年 10 万元，你想收取 20 万元的软件年费，就很难成交。

而且你的系统会产生新增成本：误拒绝正常任务、传感器维护、集成工作、恢复等待和额外审核。

**因此现在最缺的商业数字不是“消除 61.9% 不安全提交”，而是：一家真实仓库每年究竟因为虚假完成损失多少钱。**

### 3. 我会怎样估算收入天花板？

以每个站点年费 20 万元为基准，仅估算经常性软件收入：

| 付费站点 | 年经常性收入 | 投资含义 |
|---|---:|---|
| 10 | 200 万 | 验证了有限需求 |
| 50 | 1000 万 | 有机会成为垂直软件业务 |
| 200 | 4000 万 | 需要渠道化交付 |
| 500 | 1 亿元 | 必须建立跨客户、跨厂商的标准化能力 |

这不是市场容量预测，而是**收入目标反推模型**。

我的判断是：

- 作为一个独立的 AGV 事务防错插件，可能是千万级年收入的专业软件生意。
- 如果发展成跨品牌机器人执行保证与证据协议平台，才有机会进入亿元级年收入讨论。
- 但从“插件”到“平台”，绝不是多加几种故障检测就能完成的。

当前我不会按平台型公司估值。

## 四、1200 runs 消融实验：最容易被五个问题击穿

### 结论：结果很漂亮，但目前是实验室条件下的机制验证，不是工业可靠性证明

(图: B0-B3 不安全提交率柱状图)

### 攻击一：你的 B0 是不是故意设置的弱基线？

这是最危险的论文审稿攻击。

如果 B0 是一个收到“取货成功”消息就直接更新 WMS 状态的简单实现，那么 61.9% 的失败率只说明这个实现非常脆弱。

真正的工业对手会说：

> 我的系统已经有货叉传感器、任务 ACK、超时、幂等和失败重试。你为什么不用这些成熟机制作为基线？

必须增加一个 **B-Industrial** 强基线，至少具备标准任务状态、真实可获得的传感器 ACK、持久化事件日志、幂等处理、重启对账和重试机制。

然后才能检验：你的证据门控是否仍然显著优于成熟工程方案。

如果强基线的不安全提交率已经非常接近零，技术差距与商业议价能力都会急剧下降。

### 攻击二：300 runs 的零失败，不等于证明零失败率

每个变体是 10 个场景 × 30 个 seed，也就是 300 次 run。

假设每次 run 是独立的伯努利试验，而且每次仅有一个统一定义的潜在不安全提交事件：

  0/300 次观察失败的统计含义
  **约 1.0%**
  单侧 95% 置信上界，而不是风险等于 0%。
  
  如果分别审查每个故障场景，0/30 的单侧 95% 上界约为 9.5%。如果 seed 共享同一模型缺陷，独立性假设还可能不成立。

还存在一个明显的数据审计问题：如果 B0 的 61.9% 和 B1 的 4.8% 都直接按每组 300 次 run 计算，无法恰好得到这些保留一位小数的比例。

它们可能采用了“每次提交机会”或者加权平均等不同分母。这不一定是错误，但必须明确原始分子、分母和聚合公式。

否则投资人会怀疑整个数字的可复现性。

### 攻击三：物理引擎的真值是不是被当成了传感器证据？

**这是我认为整套架构最大的技术证伪点。**

在 MuJoCo 里，你可以直接得到货物真实位姿、接触状态、支撑关系及动力学数据。

但实体机器人不能直接读取“物理世界真值”。

真实设备看到的是带误差的测量：

- 货叉压力传感器可能漂移；
- 摄像头可能遮挡或者误识别；
- 货物可能先稳定后滑落；
- 叉车姿态反馈可能有延迟；
- PLC、机器人控制器和 WMS 的时钟可能不同步。

如果 B3 使用的证据实际上包含仿真真值或由真值直接构造，那么当前实验本质上是：

**拥有物理真值的系统比不知道物理真值的系统更准确。**

这个结论几乎必然成立，但远远不足以证明现实中的证据可信机制。

必须严格隔离：

`Simulation Ground Truth → 独立评分器`

和

`模拟真实传感器 → 证据裁决器 → 账本`

两边不得通过内部 API、共享状态或故障注入标志泄漏真值。

### 攻击四：你只验证了“拒绝错误”，没有充分验证“接受正确”

不安全提交率只是一个方向。

一个永远拒绝提交的系统，不安全提交率也是 0%。

你提供了 100% 任务完成率，但还需要厘清它是在什么故障分布、超时时间和恢复策略下得到的。

投资人需要四个同时存在的指标：

| 指标 | 必须证明的问题 |
|---|---|
| False Commit Rate | 没有真实完成，却被提交的比例 |
| False Reject Rate | 已真实完成，却被错误拒绝的比例 |
| Recovery Success / Time | 恢复后是否账实一致，耗时多少 |
| Throughput / Latency Penalty | 引入门控后业务吞吐牺牲多少 |

另外，B2 和 B3 的不安全提交率都是 0，说明 B3 并没有在这个指标上进一步改善。B3 的价值必须通过恢复质量、恢复时间和可用性等独立指标证明。

**0.31 秒恢复也要说明到底恢复了什么。** 是数据库状态对账、软件状态机推进，还是实体机器人重新感知、重新取货并恢复作业？这三种时间完全不可互换。

### 攻击五：10 个故障场景是否足够代表现实故障空间？

不够。

特别需要加入：

- 传感器与物理状态同时错误；
- 消息乱序、重复、长时间延迟；
- 提交成功但 ACK 丢失；
- 两个执行器争用同一货物；
- 重启后的陈旧证据被错误复用；
- 货物已移动但账本未提交；
- 账本提交后发生货物滑落；
- 长时间网络分区，以及无法自主恢复的故障。

当前 8 车异构和锁矩阵并不能自动证明上述语义正确。双机交接尚未实现，更让跨设备事务边界停留在相对简单的情况。

### 仿真到实体部署的 gap 有多大？

| 能力 | 迁移难度 | 我的判断 |
|---|---|---|
| 事务状态机、幂等与事件日志 | 中低 | 大部分可迁移 |
| 物理证据规则结构 | 中 | 规则结构可复用，阈值需要重标定 |
| 承托率、接触稳定窗 | 高 | 仿真接触信息不能直接等同于实测 |
| 自主恢复与重新观测 | 高 | 现实中需要考虑障碍、权限和人工干预 |
| 复杂车队持续运行 | 高 | 目前规模和故障覆盖不足以外推 |
| 工业安全保证 | 极高 | 另一个验证体系，不能由事务实验推出 |

NIST 关于移动机器人的测量研究明确关注滑移、地面不平、振动、动态载荷和定位异常等因素。

还需要特别纠正术语：这里的“不安全提交”主要是**业务状态错误提交**，不是已经证明了机器人的功能安全。ISO 3691-4:2023 规定的是无人驾驶工业车辆及系统的安全要求和验证，二者不能混为一谈。

**实体部署 gap：对事务软件来说中等，对物理证据可信性和自主恢复来说很大。**

## 五、从投资人视角，目前资产还缺什么？

当前材料最强的是工程说明，最弱的是独立验证与商业资产。

| 缺陷 | 严重度 | 尽调必须拿到的证据 |
|---|---|---|
| 没有真实客户及付费 | P0 | 付费 PoC、预算负责人、采购触发原因 |
| 没有硬件在环或实体实验 | P0 | 独立传感器、真实物理动作和账本闭环 |
| 没有强工业基线 | P0 | 与已有工业异常处理机制的对照 |
| 缺少原始实验审计 | P0 | 每次 run 日志、seed、故障注入、分母、代码版本 |
| 团队能力没有披露 | P0 | 机器人控制、工业集成、可靠性工程及商业负责人 |
| 缺乏 IP 权属与专利分析 | P1 | 代码权属、第三方许可、专利检索及 FTO |
| 尚无客户可复用交付模型 | P1 | 第二套设备、第二种接口、集成耗时 |
| 24h 稳定性证据不足 | P1 | 实际长稳运行数据，而不是仅有运行架构 |
| 经济指标不完整 | P1 | 每次任务成本、吞吐损失、人工异常工时 |

尤其是团队。一个工业机器人项目不是靠漂亮的 Python 测试数就能完成部署。谁负责 PLC 和现场控制器，谁为故障停线承担交付责任，谁有能力拿到工厂采购预算，这些会直接决定项目能否商业化。

同样，325 个 pytest 只说明测试集通过，不能证明测试覆盖了真实世界的重要故障。如果测试与实现由同一人按同一假设设计，必须引入独立审计或外部故障注入。

还有一个必须提交的文件是**技术资产权属清单**：哪些是原创实现、哪些依赖 MuJoCo/OR-Tools/其他开源组件、哪些可以商业分发、哪些机制已经公开发表。未来专利保护必须与开源和论文披露策略协调。

目前最值钱的是消除三个投资不确定性。

  
    
      **01**
    
    
      
        **建立真正能打的工业强基线**

        第 1–30 天
      
      对照标准 ACK、幂等、持久化重试、启动对账与工业传感器确认机制，而不是只和一个弱 B0 比较。实行盲化故障注入、证据与仿真真值隔离，公开原始统计分母。

      **验收门槛：** 新实验能同时给出 False Commit、False Reject、恢复成功率、恢复时间和吞吐损失；强基线下仍存在可重复的显著增益。否则缩减论文主张。
    
  
  
  
    
      **02**
    
    
      
        **做最小实体闭环，而不是扩大仿真**

        第 15–60 天
      
      一台真实移动机器人或可控升降执行台、一个真实负载、独立压力/位置传感器、一个外部控制器和一个企业账本服务，足够验证最核心的“物理变化不可回滚”问题。

      用设备实测证据做门控，独立方法判定实际成功或失败。注入掉电、延迟、漏报、误报及物理动作中断。

      **验收门槛：** 按故障类型累计至少 1000 次有效物理状态验证机会，并报告零失败时的统计上界；同时交付误拒率、动作耗时、故障恢复记录。不能以 0/1000 宣称工业级零风险。
    
  
  
  
    
      **03**
    
    
      
        **签下第一笔带有验收指标的真实客户订单**

        第 30–90 天
      
      优先找 WES/WCS 集成商或有异构车队的工厂，围绕一条高成本异常链做 PoC，不需要卖完整 World Model。

      建议验证目标：访谈 10 家合格买家、取得 2 家明确愿意开放技术环境的合作方、争取 1 个 10–30 万元的付费 PoC。数字是执行目标，不是销售预测。

      **验收门槛：** 合同中必须有明确预算方、真实异常基线、业务 KPI 和可归因的节约金额。免费演示视频或没有预算承诺的合作意向不能代替。
    
  

以上三项不是独立的待办清单，而是三个投资问题的连续证伪：强基线证明**技术增量**，实体闭环证明**现实可行**，付费 PoC 证明**市场需求**。

## 最终裁决

**这个项目目前最像一项有希望发展成工业软件产品的研究工程资产，而不是已经建立商业护城河的基础平台。**

它确实抓住了一个重要问题：数字系统的完成状态与不可回滚的物理动作之间可能不一致。但这个问题存在，不意味着客户必然为你的具体解决方案额外付费。

如果我是投资委员会成员，我会提出三个要求：

1. **删掉未经证实的行业独占性表述。** 不要说工业系统没有物理一致性层，要证明你的机制比现有方案多解决了什么问题。
2. **停止把仿真世界的绝对真值当成现实世界的可观测证据。** 这是理论可信度与工程可信度的分水岭。
3. **在增加功能之前证明有人购买。** 尤其是大型厂商可以内建的能力，必须尽早找到独立采购理由。

给项目团队最后一个真正需要回答的问题：

**如果明天 KUKA 或某家国产 AMR 厂商花两个月，在自己的调度系统里加上承托传感器校验、事务日志、幂等重试和故障对账，你还剩下什么无法被取代？**

如果答案只是“我们的实现更完整、测试更多”，那不是投资壁垒。

如果答案是“我们已经积累了跨厂商真实故障证据、可独立审计的提交契约、经过硬件验证的恢复能力，并且客户替换我们的代价高于采购成本”，那才是值得投资的公司。

**当前最优决策：继续孵化 90 天，以实体证据和客户付款作为下一个融资决策门槛，不按 1200 次仿真结果直接定价。**

## 三、市场与付费场景：最大问题是客户为什么不自己做

### 结论：有商业需求，但最可能的买家同时也是最可能的复制者

行业大市场并不小。Interact Analysis 在 2026 年 1 月预测，全球移动机器人市场收入将从 2024 年不足 50 亿美元增长到 2030 年约 140 亿美元。

但这个数字对你几乎没有直接估值意义。它包括机器人硬件与整体系统收入，不是“执行证据软件”的可服务市场。

### 1. 客户优先级与收费能力

以下价格是**建议测试的合同区间，不是已经验证的市场成交价格**，金额均为人民币。

| 客户类型 | 痛点和支付意愿 | 可测试价格 | 优先级 |
|---|---|---|---|
| AMR/AGV 厂商 | 设备误报完成、客户索赔、售后排障 | 30–150 万/年 OEM 框架授权 | 高 |
| WES/WCS 集成商 | 跨设备异常恢复、账实不同步 | 8–30 万/站点/年 | 最高 |
| 终端工厂/仓库 | 库存差异、停线、异常人工处置 | 8–30 万/站点/年 | 中高 |
| WMS 软件厂商 | 机器人任务状态可信度 | 联合项目或 OEM 授权 | 中 |
| 仿真软件厂商 | 故障注入、测试和验证 | 5–20 万/年工具许可 | 低 |

我认为**第一批客户应该是复杂项目的 WES/WCS 系统集成商，而不是终端工厂，也不是最大的 AMR 厂商。**

原因很直接：

大型 AMR 厂商有研发能力，倾向于自己实现。终端工厂通常不会为了物理证据门控单独引入一套核心软件；而集成商长期处于机器人系统与客户 WMS/MES 的交界处，最容易为两边责任不清、异常人工对账付出成本。

然而，集成商也可能选择自己开发。你必须证明购买比自研便宜，并且能降低项目交付与售后成本。

### 2. 你还没建立客户 ROI

假设某仓库每年有 100 万次货物移动任务，每次虚假完成平均造成 1000 元的排障、人工处理和业务损失。

  假设场景：虚假完成的年度经济损失
  
    
      
        虚假完成率 0.01%
        **10 万元/年**
        100 次 × 1000 元
      
    
    
      
        虚假完成率 0.1%
        **100 万元/年**
        1000 次 × 1000 元
      
    
  
  纯情景假设，不代表真实行业发生率或平均损失。

如果客户实际损失只有每年 10 万元，你想收取 20 万元的软件年费，就很难成交。

而且你的系统会产生新增成本：误拒绝正常任务、传感器维护、集成工作、恢复等待和额外审核。

**因此现在最缺的商业数字不是“消除 61.9% 不安全提交”，而是：一家真实仓库每年究竟因为虚假完成损失多少钱。**

### 3. 我会怎样估算收入天花板？

以每个站点年费 20 万元为基准，仅估算经常性软件收入：

| 付费站点 | 年经常性收入 | 投资含义 |
|---|---:|---|
| 10 | 200 万 | 验证了有限需求 |
| 50 | 1000 万 | 有机会成为垂直软件业务 |
| 200 | 4000 万 | 需要渠道化交付 |
| 500 | 1 亿元 | 必须建立跨客户、跨厂商的标准化能力 |

这不是市场容量预测，而是**收入目标反推模型**。

我的判断是：

- 作为一个独立的 AGV 事务防错插件，可能是千万级年收入的专业软件生意。
- 如果发展成跨品牌机器人执行保证与证据协议平台，才有机会进入亿元级年收入讨论。
- 但从“插件”到“平台”，绝不是多加几种故障检测就能完成的。

当前我不会按平台型公司估值。

## 四、1200 runs 消融实验：最容易被五个问题击穿

### 结论：结果很漂亮，但目前是实验室条件下的机制验证，不是工业可靠性证明

(图: B0-B3 不安全提交率柱状图)

### 攻击一：你的 B0 是不是故意设置的弱基线？

这是最危险的论文审稿攻击。

如果 B0 是一个收到“取货成功”消息就直接更新 WMS 状态的简单实现，那么 61.9% 的失败率只说明这个实现非常脆弱。

真正的工业对手会说：

> 我的系统已经有货叉传感器、任务 ACK、超时、幂等和失败重试。你为什么不用这些成熟机制作为基线？

必须增加一个 **B-Industrial** 强基线，至少具备标准任务状态、真实可获得的传感器 ACK、持久化事件日志、幂等处理、重启对账和重试机制。

然后才能检验：你的证据门控是否仍然显著优于成熟工程方案。

如果强基线的不安全提交率已经非常接近零，技术差距与商业议价能力都会急剧下降。

### 攻击二：300 runs 的零失败，不等于证明零失败率

每个变体是 10 个场景 × 30 个 seed，也就是 300 次 run。

假设每次 run 是独立的伯努利试验，而且每次仅有一个统一定义的潜在不安全提交事件：

  0/300 次观察失败的统计含义
  **约 1.0%**
  单侧 95% 置信上界，而不是风险等于 0%。
  
  如果分别审查每个故障场景，0/30 的单侧 95% 上界约为 9.5%。如果 seed 共享同一模型缺陷，独立性假设还可能不成立。

还存在一个明显的数据审计问题：如果 B0 的 61.9% 和 B1 的 4.8% 都直接按每组 300 次 run 计算，无法恰好得到这些保留一位小数的比例。

它们可能采用了“每次提交机会”或者加权平均等不同分母。这不一定是错误，但必须明确原始分子、分母和聚合公式。

否则投资人会怀疑整个数字的可复现性。

### 攻击三：物理引擎的真值是不是被当成了传感器证据？

**这是我认为整套架构最大的技术证伪点。**

在 MuJoCo 里，你可以直接得到货物真实位姿、接触状态、支撑关系及动力学数据。

但实体机器人不能直接读取“物理世界真值”。

真实设备看到的是带误差的测量：

- 货叉压力传感器可能漂移；
- 摄像头可能遮挡或者误识别；
- 货物可能先稳定后滑落；
- 叉车姿态反馈可能有延迟；
- PLC、机器人控制器和 WMS 的时钟可能不同步。

如果 B3 使用的证据实际上包含仿真真值或由真值直接构造，那么当前实验本质上是：

**拥有物理真值的系统比不知道物理真值的系统更准确。**

这个结论几乎必然成立，但远远不足以证明现实中的证据可信机制。

必须严格隔离：

`Simulation Ground Truth → 独立评分器`

和

`模拟真实传感器 → 证据裁决器 → 账本`

两边不得通过内部 API、共享状态或故障注入标志泄漏真值。

### 攻击四：你只验证了“拒绝错误”，没有充分验证“接受正确”

不安全提交率只是一个方向。

一个永远拒绝提交的系统，不安全提交率也是 0%。

你提供了 100% 任务完成率，但还需要厘清它是在什么故障分布、超时时间和恢复策略下得到的。

投资人需要四个同时存在的指标：

| 指标 | 必须证明的问题 |
|---|---|
| False Commit Rate | 没有真实完成，却被提交的比例 |
| False Reject Rate | 已真实完成，却被错误拒绝的比例 |
| Recovery Success / Time | 恢复后是否账实一致，耗时多少 |
| Throughput / Latency Penalty | 引入门控后业务吞吐牺牲多少 |

另外，B2 和 B3 的不安全提交率都是 0，说明 B3 并没有在这个指标上进一步改善。B3 的价值必须通过恢复质量、恢复时间和可用性等独立指标证明。

**0.31 秒恢复也要说明到底恢复了什么。** 是数据库状态对账、软件状态机推进，还是实体机器人重新感知、重新取货并恢复作业？这三种时间完全不可互换。

### 攻击五：10 个故障场景是否足够代表现实故障空间？

不够。

特别需要加入：

- 传感器与物理状态同时错误；
- 消息乱序、重复、长时间延迟；
- 提交成功但 ACK 丢失；
- 两个执行器争用同一货物；
- 重启后的陈旧证据被错误复用；
- 货物已移动但账本未提交；
- 账本提交后发生货物滑落；
- 长时间网络分区，以及无法自主恢复的故障。

当前 8 车异构和锁矩阵并不能自动证明上述语义正确。双机交接尚未实现，更让跨设备事务边界停留在相对简单的情况。

### 仿真到实体部署的 gap 有多大？

| 能力 | 迁移难度 | 我的判断 |
|---|---|---|
| 事务状态机、幂等与事件日志 | 中低 | 大部分可迁移 |
| 物理证据规则结构 | 中 | 规则结构可复用，阈值需要重标定 |
| 承托率、接触稳定窗 | 高 | 仿真接触信息不能直接等同于实测 |
| 自主恢复与重新观测 | 高 | 现实中需要考虑障碍、权限和人工干预 |
| 复杂车队持续运行 | 高 | 目前规模和故障覆盖不足以外推 |
| 工业安全保证 | 极高 | 另一个验证体系，不能由事务实验推出 |

NIST 关于移动机器人的测量研究明确关注滑移、地面不平、振动、动态载荷和定位异常等因素。

还需要特别纠正术语：这里的“不安全提交”主要是**业务状态错误提交**，不是已经证明了机器人的功能安全。ISO 3691-4:2023 规定的是无人驾驶工业车辆及系统的安全要求和验证，二者不能混为一谈。

**实体部署 gap：对事务软件来说中等，对物理证据可信性和自主恢复来说很大。**

## 五、从投资人视角，目前资产还缺什么？

当前材料最强的是工程说明，最弱的是独立验证与商业资产。

| 缺陷 | 严重度 | 尽调必须拿到的证据 |
|---|---|---|
| 没有真实客户及付费 | P0 | 付费 PoC、预算负责人、采购触发原因 |
| 没有硬件在环或实体实验 | P0 | 独立传感器、真实物理动作和账本闭环 |
| 没有强工业基线 | P0 | 与已有工业异常处理机制的对照 |
| 缺少原始实验审计 | P0 | 每次 run 日志、seed、故障注入、分母、代码版本 |
| 团队能力没有披露 | P0 | 机器人控制、工业集成、可靠性工程及商业负责人 |
| 缺乏 IP 权属与专利分析 | P1 | 代码权属、第三方许可、专利检索及 FTO |
| 尚无客户可复用交付模型 | P1 | 第二套设备、第二种接口、集成耗时 |
| 24h 稳定性证据不足 | P1 | 实际长稳运行数据，而不是仅有运行架构 |
| 经济指标不完整 | P1 | 每次任务成本、吞吐损失、人工异常工时 |

尤其是团队。一个工业机器人项目不是靠漂亮的 Python 测试数就能完成部署。谁负责 PLC 和现场控制器，谁为故障停线承担交付责任，谁有能力拿到工厂采购预算，这些会直接决定项目能否商业化。

同样，325 个 pytest 只说明测试集通过，不能证明测试覆盖了真实世界的重要故障。如果测试与实现由同一人按同一假设设计，必须引入独立审计或外部故障注入。

还有一个必须提交的文件是**技术资产权属清单**：哪些是原创实现、哪些依赖 MuJoCo/OR-Tools/其他开源组件、哪些可以商业分发、哪些机制已经公开发表。未来专利保护必须与开源和论文披露策略协调。

## 最终裁决

**这个项目目前最像一项有希望发展成工业软件产品的研究工程资产，而不是已经建立商业护城河的基础平台。**

它确实抓住了一个重要问题：数字系统的完成状态与不可回滚的物理动作之间可能不一致。但这个问题存在，不意味着客户必然为你的具体解决方案额外付费。

如果我是投资委员会成员，我会提出三个要求：

1. **删掉未经证实的行业独占性表述。** 不要说工业系统没有物理一致性层，要证明你的机制比现有方案多解决了什么问题。
2. **停止把仿真世界的绝对真值当成现实世界的可观测证据。** 这是理论可信度与工程可信度的分水岭。
3. **在增加功能之前证明有人购买。** 尤其是大型厂商可以内建的能力，必须尽早找到独立采购理由。

给项目团队最后一个真正需要回答的问题：

**如果明天 KUKA 或某家国产 AMR 厂商花两个月，在自己的调度系统里加上承托传感器校验、事务日志、幂等重试和故障对账，你还剩下什么无法被取代？**

如果答案只是“我们的实现更完整、测试更多”，那不是投资壁垒。

如果答案是“我们已经积累了跨厂商真实故障证据、可独立审计的提交契约、经过硬件验证的恢复能力，并且客户替换我们的代价高于采购成本”，那才是值得投资的公司。

**当前最优决策：继续孵化 90 天，以实体证据和客户付款作为下一个融资决策门槛，不按 1200 次仿真结果直接定价。**
