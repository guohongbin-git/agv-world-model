# DC 数字孪生 v0.4｜架构审查（第四轮）

  REJECT — 不批准 v0.4 冻结
  2026-10-13｜设计级审查，未执行仓库代码

## 一、总体裁决：方向正确，但架构核心尚未闭合

这份 v0.4 相比一般的数字孪生概念方案，更有实际工程基础，也已经纠正了一些明显的叙事问题。但三轮自审主要修正了**命名、工作量、实验数字和风险措辞**，尚未解决几个真正决定架构是否成立的问题。

  架构审查评分
  
    
      **72/100**
      设计完整性
    
    
      **54/100**
      当前验收可信度
    
  
  
  **主要阻断项：**
  - P0 账实一致性验证存在自我证明风险。
  - P1 摄像头与 LiDAR 只是消费者分开，观测独立性没有建立。
  - 核心事务语义没有明确扩展到卡车装卸。
  - `dc-twin` 与 `agv-warehouse-core` 的依赖方向存在倒置风险。
  - 缺少连接仿真、观测、执行证据与账本的统一时间和状态契约。

**我的总体判断：应该保留独立项目方案，但不能直接进入 P0–P3 开发。需要先补一个 P-1：契约与验证基建。**

否则极可能出现一种结果：四期全部 PASS、演示片非常漂亮、pytest 全绿，但实际上只完成了一个能自洽运行的仿真演示，并没有增加多少可独立审计的执行可信能力。

还有一个必须立即纠正的硬错误：

**P2 场景矩阵算错了。**

\[
3\text{（车队）}\times2\text{（月台）}\times3\text{（到达）}\times30
=\boxed{540\text{ runs}}
\]

不是设计稿声称的 810 runs。3×3×1 摸底也不是原矩阵的有效子集，除非重新定义第三个维度的含义。

这不是严重的算法错误，但经过三轮自审仍未发现，说明配置定义、实验计划和报告数字之间尚未建立单一数据源。

## 二、§7 分层架构：最大的错误是把“场景能力”当成“执行可信架构”

### 2.1 NVIDIA 对标混合了两个不同技术体系

这是 §1 和 §7 中必须修改的事实性问题。

当前稿件暗含这样的对比：

> PepsiCo / NVIDIA 是视觉和运动学展示；我们具有真正的物理仿真与执行闭环。

这个对比不成立。

核对官方资料后，应区分：

| 体系 | 官方公开能力 | 正确对标方式 |
|---|---|---|
| NVIDIA VSS 3.0 Warehouse Blueprint | 2D/3D 视频感知、多摄像头跟踪、行为分析、ROI 事件、Agent、SDG | 对标视觉感知与场景分析 |
| PepsiCo + Siemens + NVIDIA Digital Twin Composer | 设施、设备、物流路径的高保真仿真、物理级精度、方案验证与吞吐优化 | 对标物理仿真与 What-if |
| 你的 `dc-twin` | MuJoCo + 任务执行 + 物理证据门控 + 账本恢复 | 对标执行证据与事务一致性 |

NVIDIA VSS 的官方 3D Profile 确实以多摄像头感知、跟踪和事件分析为主。

但 PepsiCo 和 Siemens 2026 年公开的 Digital Twin Composer 案例明确涉及物理级精度的设施模拟、配置验证和吞吐优化，而不只是运动学展示。

因此：

- “他们是运动学演示，我们物理可证”——**删除**。
- “他们无闭环”——必须说明是哪一种闭环，不能一概而论。
- “Blueprint 体系缺失执行可信层”——最多表述为“所核查的公开资料未明确展示与本项目同等语义的物理证据—账本原子提交协议”。

你真正不同的是**执行证据与业务状态提交的耦合机制**，不是拥有物理引擎本身。

另外，VSS 也并非完全没有数字孪生与仿真支撑。官方 SDG 文档明确将仿真、真值生成及 Sim2Real 用于多摄像头系统开发和验证。

### 2.2 v0.4 缺少真正的架构主干

现在的设计以功能块组织：

MuJoCo → 摄像头 → 融合 → 门控 → KPI → Blender。

但**功能排列不等于系统架构**。

缺少四条关键边界：

1. 物理仿真状态与设备可观测状态的边界。
2. 观测事实与可以授权事务提交的证据的边界。
3. 仓内任务与场站外运输业务的边界。
4. 仿真执行系统与数字孪生展示、实验分析系统的边界。

我建议 v0.5 改成下面的结构：

  
    **dc-twin：场景与实验编排层**

    Facility / Dock / Truck Scenario · Scenario Runner · KPI · UI · Blender Export
  
  
    <icon name="arrow-down-up" color="secondary"/>
    版本化 Scene / Run / Event 契约
  
  
    
      
        **执行域（core）**

        调度、锁矩阵、执行、证据判定、事务账本、恢复
      
    
    
      
        **观测域（adapter）**

        传感器仿真、感知事件、融合、时间同步、证据来源
      
    
  
  
    <icon name="arrow-down-up" color="secondary"/>
    受控状态读取 / 观测输出
  
  
    **MuJoCo 物理世界**

    车辆、货物、碰撞、接触、场景动力学
  
  
    <icon name="arrow-down" color="secondary"/>
  
  
    **独立验证域（Evaluator）**

    Ground Truth / 守恒不变量 / Safety Oracle / 故障注入审计
    不得作为执行域的运行时证据来源
  

图为建议的逻辑架构，不代表必须部署成多个微服务；仿真世界同时给观测适配器和独立验证器提供状态，但两条路径必须隔离。

**特别强调：执行可信层必须是架构主角，场景、美术和 Agent 都只能围绕它扩展。**

你现在还应该把核心对象从一个笼统的 `Event` 拆成至少四种语义：

| 对象 | 代表什么 |
|---|---|
| `Observation` | 某传感器在某时刻报告了什么 |
| `EvidenceVerdict` | 基于哪些观测、哪套规则作出了何种证据裁决 |
| `ExecutionEvent` | 哪个执行动作进入了什么阶段 |
| `LedgerTransaction` | 企业账本发生了什么状态变更 |

四者之间必须有可追溯的引用关系。不能通过一个 `type/confidence/ts/source` 的视觉事件直接得到 COMMITTED。

### 2.3 Agent 的位置错了

P2 增加“证据审计 Agent”可以作为展示，但不能让它介入证据裁决的核心路径。

原因有三点：

- 确定性事务判定不需要 LLM。
- Agent 无法成为物理事实的可信来源。
- Agent 输出的自然语言不应改变账本提交结果。

正确边界是：

**Evidence Engine 作出确定性裁决 → Agent 解释异常、查询历史、建议人工处理。**

Agent 只能读取证据快照并提出建议，不能改写历史证据，也不能在没有独立授权的情况下重试或提交物理动作。

没有这个边界，后续很容易把“Agent 能解释为什么拒单”误当成“Agent 增强了执行可信性”。

## 三、P0–P3：验收判据看似量化，但部分属于伪验收

### 3.1 逐期裁决

| 阶段 | 当前验收 | 裁决 | 主要问题 |
|---|---|---|---|
| P0 | 30min sim、≥1 卡车、账实相等、pytest 全绿 | FAIL | 一次成功不证明异常事务正确 |
| P1 | unsafe=0、false reject≤5%、吞吐损失≤10% | FAIL | 可观测性不足，统计基线和指标定义不完整 |
| P2 | 矩阵扫描、KPI 曲面报告 | WEAK | 有报告不等于完成优化，也不证明结论有效 |
| P3 | 60–90 秒成片 | WEAK | 只检验视频长度，不检验数据真实性和可重放性 |

### 3.2 P0 最大漏洞：账实相等可能是同一系统自我证明

你的验收式是：

`账本托盘集合 = truth 物理集合`

首先，集合相等究竟代表什么？

一个托盘可以位于货架、AGV、交接台、月台、卡车、运输途中，甚至已经离开仿真边界。业务账本中的库存归属又可能和它的物理位置不同。

因此不能简单地比较两个托盘 ID 集合。

建议至少建立三个独立状态域：

- **物理位置**：托盘实际在哪里，由仿真真值判定。
- **业务归属/保管责任**：该托盘在 WMS 或运输交接记录里属于谁。
- **事务状态**：操作待执行、执行中、证据待确认、已提交、待恢复等。

例如，托盘已装车而出库事务尚未提交，是需要标注的短暂账实分歧，不应被错误地直接当作系统故障；但若证据迟迟未到，必须进入可恢复状态，而不能静默消失。

真正的物理守恒应当是：

\[
P_{\text{initial}}+P_{\text{received}}
=P_{\text{onsite}}+P_{\text{truck}}+P_{\text{departed}}
+P_{\text{other accounted}}
\]

这里比较的应是**逐托盘 ID 的不重不漏归属**，不是只比较数量。`departed` 必须由可信的边界转移记录维护，不能因为删除了 MuJoCo 中的货物几何体就认定它已经发运。

更重要的是，独立 Evaluator 必须从物理状态重建实际归属，而不是读取账本生成的托盘归属结果。

否则 Dispatcher 写错位置，Evaluator 又复用了 Dispatcher 的逻辑，两边一致，一样可以 PASS。

**建议 P0 强制增加六条负向测试：**

1. 未装车却收到装车完成事件，必须拒绝提交。
2. 货物装上错误卡车，不能以“已装车”通过。
3. 已装车但提交前进程崩溃，重启后必须能识别并恢复。
4. 已提交但确认消息丢失，重复执行不能导致重复出库。
5. 卡车未到、已离场或货位被占用时，错误装车指令必须被拒绝。
6. 卡车离场时，不能发生货物凭空消失、重复存在或未经核验的隐式转移。

`≥1 辆卡车完成装车离场` 只能证明 happy path 可运行，不能证明事务闭环。

还有一个实质问题：**静态 mocap 卡车不等于完成了物理意义上的装车与离场。**

如果装车只是把托盘状态绑定到卡车，离场只是隐藏对象或移出场景，那么它属于抽象物流交接模型。可以作为 P0，但必须明确说明，没有验证真实装车碰撞、货物固定或车辆行驶动力学。

### 3.3 P1 的三个百分比可能互相矛盾

你指定漏检 20%、误检 5%，同时要求 false reject≤5%。

如果摄像头检测是每次正确装车提交的必需条件，又没有独立的恢复观测，那么单次漏检 20% 就会造成约 20% 的正确事件无法获得视觉确认。

要做到最终误拒不超过 5%，必须引入额外机制，例如多帧观测、其他传感器佐证、重观测或明确的超时恢复。

这本身完全可以做到，但不能省略机制、重试预算和等待时间。

更严重的是，你没有说明三个指标的分母。

| 指标 | 应采用的定义 |
|---|---|
| Unsafe commit | 不真实成立但已提交的事务数 / 实际不成立的提交机会数 |
| False reject | 真实成立却被最终拒绝的事务数 / 真实成立的事务数 |
| Throughput loss | 同需求、同故障暴露下，配对基线与实验组的单位 sim time 有效完成量之差 |
| Recovery time | 从故障发生或首次可检测时刻至账实一致恢复的时间分布 |

临时 `DEFERRED`、超时 `REJECTED` 和最终 `ABORTED` 必须区分。否则可以通过无限期等待来同时制造“0 不安全提交”和“0 最终误拒”。

**建议 P1 必须设置三种对照：**

- 正常物理完成 + 感知正常。
- 正常物理完成 + 感知失效。
- 物理未完成 + 感知错误声称完成。

第三种最重要，因为它直接攻击错误提交。

单纯观察一个原本 unsafe=0 的系统在添加摄像头后仍为 0，不能证明摄像头产生了增量价值。

### 3.4 P2 根本还不是优化器

枚举 540 组实验结果（包含 seed），并绘制 KPI 曲面，这叫**参数扫描或仿真试验设计**，还不能称作 What-if 优化器。

一个优化器至少需要：

- 明确决策变量，例如车辆数、月台数、到达调度策略。
- 明确目标函数，例如最大化有效吞吐，同时惩罚异常处理时间和车辆成本。
- 明确可行域与约束，例如月台容量、道路通行、车队类型兼容性。
- 明确选择规则与独立验证数据，避免在训练或选择用的 30 seed 上报最优成绩。

另外，到达时刻表不等于到达强度。`到达 1/2/3` 必须规定是每小时到达率、泊位需求批次，还是三个场景类别；否则 KPI 不能跨配置比较。

**应当先建立小规模参数扫描，再增加优化选点和留出 seed 验证。**

例如先用 20 个 seed 选择配置，再用另外 10 个未参与选择的 seed 比较候选方案与基线。这个分组只是一种起点；真正置信区间仍要看方差和相关性。

还有一个时间问题：30 分钟的模拟时间在 1kHz 下对应 180 万个物理 step。相同物理时间的运行成本可能因车辆数、摄像头 raycast 数量和场景碰撞数量差异巨大。

所以 P2 必须报告：

- 仿真时长 `sim_t`；
- 实际耗时 `wall_t`；
- Real-Time Factor：`sim_t/wall_t`；
- 求解器时延、证据判定时延以及关键任务响应时延。

仅有门控延迟 p95、没有整条执行链延迟，不足以支持性能结论。

### 3.5 P3 不应该以视频长度验收

Blender 成片最容易制造一种假进展：物理与执行数据没有闭合，视觉质量却迅速提高。

把 P3 验收改为：

**同一 `run_id` 的物理状态、事件流、事务裁决和渲染结果可以追溯与重放。**

60–90 秒只是交付格式。

必须能够从画面某一秒追到对应的模拟时刻、车辆、托盘、操作、证据和账本版本。镜头可以插值、调色和艺术化，但不能通过插帧创造不存在的作业完成事件。

## 四、虚拟摄像头与感知融合：这是全稿技术风险最高的部分

### 4.1 最大结构性错误：消费者分开，不等于信息源独立

v0.4 认为：

`LiDAR → 避障`

`Camera → 门控`

因此两者互不越界。

但两条支路可能都从同一个 MuJoCo 几何真值中生成观测。

这不是绝对错误——仿真传感器当然需要读取虚拟物理世界。错误在于把**两个软件消费者**误认为**两个统计独立的传感器证据源**。

假设车辆姿态、托盘位置或仿真几何本身存在系统性偏差，两条通道可能一起产生同方向的错误。

因此，“两个传感器同时确认”的可信性不能直接按独立概率相乘。

必须定义共同原因故障模型，并测试相关错误。

### 4.2 `mj_ray` 不是摄像头模型

MuJoCo 官方 API 将 `mj_ray` 定义为物理几何体的射线相交查询。它适合做距离、遮挡和可见性模拟，但不会天然输出图像目标检测的误差结构。

如果用它命中托盘几何体，再直接生成：

`pallet_id / confidence / timestamp`

你模拟的其实是**带噪声的对象存在事件**，不是真正的视觉识别。

它很可能跳过现实中最困难的环节：

- 2D 目标检测；
- 相机标定误差；
- 遮挡和截断；
- 目标跟踪；
- 多目标身份关联；
- 像素到世界坐标的投影误差。

尤其是 `pallet_id`。如果摄像头事件直接读取 MuJoCo 的真实对象 ID，融合层就不需要做目标关联，恰好绕过了最困难的感知问题。

**不要把 Synthetic Detection Event 称为已实现的 Vision AI。**

### 4.3 建议明确两级感知实现

| 级别 | 实现 | 可以验证什么 |
|---|---|---|
| P1a：事件级传感器模拟 | 几何射线、可见性、噪声、延迟、误识别 | 证据融合及事务系统对不可靠观测的鲁棒性 |
| P1b：图像级虚拟摄像头 | RGB 渲染、开源检测器、跟踪、标定、2D/3D 关联 | 真正的视觉感知误差传播 |

P1a 应先完成，因为这是事务架构实验最需要的能力。

P1b 才用于对标真实视觉管线。如果不实现 P1b，可以把它排除在当前范围外，但公开表述只能是“合成观测事件融合”。

### 4.4 噪声模型不能只有漏检 × 误检二维网格

漏检和误检是结果统计，不是完整的成因模型。

至少需要四类扰动：

| 类别 | 必要参数 |
|---|---|
| 空间误差 | 位姿偏差、标定漂移、遮挡、视野边缘退化 |
| 时间误差 | 采集延迟、传输延迟、乱序、丢帧、时钟偏差 |
| 关联误差 | ID switch、重复检测、错误托盘关联 |
| 相关故障 | 多帧连续失效、共用标定偏差、多个传感器同时错误 |

其中时间误差非常关键。

**一条完全准确、但已经过期的摄像头观测，不应该被允许确认当前装车成功。**

建议证据对象必须显式携带以下信息：

```text
run_id
evidence_id
operation_id
subject_id / asserted_identity
sensor_id
capture_sim_t
arrival_sim_t
source_sequence
observation_type
measurement
confidence
sensor_model_version
calibration_version
```

证据裁决另外携带：

```text
verdict_id
operation_id
evidence_refs
rule_version
decision_sim_t
expiry_sim_t
decision
reason_codes
```

这里 `source_sequence` 和 `operation_id` 比单纯的 timestamp 更重要：前者帮助识别重复、乱序，后者防止把上一次装车的证据用来确认下一次任务。

另外，**confidence 不能当成物理事实概率直接使用**。它需要校准，而且不同传感器的置信度通常不能简单相乘。

### 4.5 缺失“传感器能证明什么”的证据能力矩阵

摄像头能看到托盘进入车厢，不代表能证明承托充分、装载稳定、固定到位，更不能单独证明货物已经到达另一座配送中心。

建议强制建立：

| 事实主张 | 可接受的主要证据 |
|---|---|
| 托盘进入月台 ROI | 摄像头或位置传感器 |
| 托盘身份 | 标签识别、任务关联、RFID 等 |
| 已完成物理装载 | 货叉/支撑状态 + 位置 + 稳定窗 |
| 装车目标正确 | 任务 ID + 卡车 ID + 托盘身份 |
| 卡车已离场 | 月台离场传感器或经过独立模拟的边界事件 |
| 运输途中 | 运输系统定位或运输状态报告，属于另一个证据域 |
| 目的地已接收 | 目的地独立签收与卸货确认 |

P1 不需要全部实现，但必须先定义证据能力边界。

否则用一条 Camera ROI 事件确认实际承托，属于**拿不具备证明能力的观测去证明更强的物理命题**。

## 五、§8 独立项目与组合契约：仓库边界划得还不够干净

### 5.1 我支持独立仓库，但不支持当前的 API 暴露方式

`dc-twin` 作为独立 repo 是合理的。问题在这句：

> dc-twin 只 import 内核 API（cell/ledger/证据事务/demand/渲染）

这句话看起来遵守封装，实际可能把整个内部实现都暴露出去。

如果 `dc-twin` 能直接操作 `cell`、`ledger`、`demand` 的内部对象，那么它很容易：

- 在外部直接改变货物位置；
- 绕开事务协议修改账本；
- 对核心调度数据结构产生版本依赖；
- 将 DC 场景逻辑渗入核心代码。

最终只是从一个大仓库变成两个高度耦合的仓库。

**需要暴露的是能力协议，而不是内部模块。**

建议公共边界如下：

| Core 对外能力 | DC 层应该如何使用 |
|---|---|
| `WarehouseRuntime` | 创建、启动、推进和停止模拟 |
| `ScenarioConfig` | 注入合法的场景配置 |
| `OperationCommand` | 提交装卸、移动和交接请求 |
| `EvidencePolicy` | 注册版本化的证据判定规则 |
| `ObservationPort` | 接收类型化观测，而非读取物理真值 |
| `EventStream` | 订阅事务状态与执行结果 |
| `ReadModel` | 读取账本投影，不直接变更账本 |
| `WorldAdapter` | 以受控方式连接物理实现 |

这些是建议的抽象名称，不代表当前代码已有对应接口。

我特别反对让场景层直接使用内部 `Ledger.commit()`。业务提交必须经过核心定义的命令和裁决路径。

### 5.2 `agv-warehouse-core` 打包的主要坑

| 坑 | 后果 | 必需措施 |
|---|---|---|
| 隐式依赖项目根目录 | 从别的 repo 调用就失败 | `src/` layout，wheel 安装测试 |
| MJCF、贴图、配置没有打包 | 本地能跑，安装版缺资源 | 使用包资源机制并验证 wheel 内容 |
| 顶层 import 启动服务或 UI | core 无法无头运行 | 分离库初始化与演示入口 |
| core 反向 import `dc-twin` | 双向依赖 | 插件注册或接口注入 |
| 改造原仓导致旧仿真行为改变 | 1200 runs 无法复现 | 旧实验锁定版本与配置 |
| MuJoCo/求解器版本漂移 | 结果数值和性能改变 | 依赖版本、环境信息、回归基准 |
| Blender 与 GUI 被打入核心依赖 | 部署沉重、许可关系复杂 | 渲染独立进程与可选组件 |

Python Packaging 官方也明确说明，`src` 布局有助于防止测试意外引用源码目录而非实际安装的包。

因此打包验收不能是：

`pip install -e . && pytest`

必须额外验证：

1. 构建正式 wheel。
2. 在全新环境、不同工作目录安装。
3. 不依赖源仓库路径执行核心示例。
4. 使用安装版 wheel 运行契约测试。
5. 原有 8 车模型、事务测试和确定性基准保持兼容。

新包先使用 `0.x` 版本并显式管理契约演进，等公共 API 和兼容性边界稳定后再承诺正式稳定版本。

### 5.3 最危险的是兼容性升级悄悄改变证据语义

假设新版本改了稳定窗阈值、托盘身份关联规则，或者装车提交时刻。

这些修改可能不改变 API 签名，却改变历史实验结果。

普通语义化版本管理不够。至少要同时版本化：

`core_version`、`scenario_schema_version`、`evidence_policy_version`、`sensor_model_version`、`experiment_manifest_version`。

任何影响事务裁决结果的改动，都必须触发证据契约回归，而不是仅跑接口测试。

这里最应该保持独立的是 **Execution Evidence Protocol**，而不是卡车模型、摄像头实现或 Blender 导出器。

### 5.4 纯开源承诺基本可行，但不要说“纯开源 pip 栈”

MuJoCo 的源码采用 Apache-2.0 许可；Blender 使用 GPL 许可。二者都属于开源软件，但 Blender 不是普通 Python pip 依赖，也不能不核查许可关系就将其与全部代码混合分发。

建议把承诺改为：

**“核心运行和实验能力无需 NVIDIA 专有运行时、SDK 或许可工件；采用经过依赖与许可审计的开源组件。”**

对应验收必须有 SBOM、许可清单和无 NVIDIA GPU/驱动依赖的干净环境运行测试。不能只检查 `requirements.txt` 是否包含 NVIDIA 字符串。

## 六、§8.4 运输车队预留：确实过早，而且抽象方向不对

### 6.1 `BerthTruck / RoadTruck` 不应该是同一 Agent 的简单双态

两者在业务语义上差别很大：

| 维度 | BerthTruck | RoadTruck |
|---|---|---|
| 核心问题 | 月台装卸、货物保管交接 | 路由、在途监控、ETA、异常运输 |
| 物理空间 | 单一仓库仿真场景 | 道路网络与多个场站 |
| 时间尺度 | 秒、分钟 | 小时、天 |
| 控制模型 | 月台占用与装卸确认 | TMS/车辆远程状态 |
| 证据来源 | 装卸、位置、接触观测 | GPS、电子封签、签收、运输事件 |

这不只是对象增加一个 `RoadTruck` 子类，而是跨越新的业务限界上下文。

**v0.4 应删除 RoadTruck 类型预留，保留稳定的跨边界业务标识。**

例如：

`facility_id`、`shipment_id`、`vehicle_id`、`load_unit_id`、`handoff_id`。

未来运输车队由独立 Transport/TMS 模块接管，消费已确认的装车和发运事件即可。

### 6.2 “装车/在途/到货/卸车四态共用证据协议”也不准确

这四个可以共享事件信封格式，但不应该共享物理证明规则。

“装车成立”的判据，与“车辆到货成立”的判据根本不同。它们属于不同证据类型和责任主体。

同时，不能把装车、在途、到货、卸车混成四个互相独立的事实而没有状态转移约束。例如：

- 未发运不能确认在途；
- 未到达不能确认卸货；
- 重复到货消息不能产生第二次入库；
- 发运证据不自动授予目的地收货权限。

最小可行扩展应该是：

`Loaded → HandoffConfirmed → Departed`

到这里就停止 P0 的职责。

### 6.3 VDA 5050 不是公路运输接口

VDA 5050 面向移动机器人与主控系统的通信，不是干线卡车的 TMS 协议。

将来需要多 DC 运输网络时，应该重新审查运输状态、运输任务和设备控制模型，不应因为现在有 AGV 协议就强行复用。

**裁决：删除 RoadTruck 具体类型，保留事件化的跨场站交接边界。**

## 七、三轮自审遗漏的七个致命盲点

下面这些是我认为 v0.4 最需要补入风险登记的项目。

### P0-1：装车腿复用 `trunk`，存在语义污染

自审#1 把“装车腿复用 trunk”当成降低改动量的优化。

我不认可这个决定直接通过。

如果 `trunk` 在现有系统中代表仓内干线移动，那么其完成条件可能只是到达目标点；装车则需要确认正确托盘、正确车辆、接触/支撑、交接责任和业务提交。

**类型复用只有在动作语义及其不变量一致时才安全。**

正确方案是尽可能复用底层移动和调度能力，但明确新增装车操作的业务类型与完成规则。

否则系统可能出现：

`到达 tk 节点 → trunk 完成 → 直接出库提交`

这是对证据门控设计目标的直接破坏。

### P0-2：数据库事务与物理动作仍然存在不可消除的非原子窗口

v0.4 没有在 DC 场景里重新检查这个问题。

例如：

1. 机器人已经把托盘放上卡车。
2. 物理装车成功。
3. 系统在账本提交之前崩溃。
4. 重启后无法确认这次动作是否已经发生。

数据库事务不可能让已发生的物理动作回滚。

正确机制必须包括动作前持久化意图、操作幂等、完成后的证据裁决以及异常后的重新观测与对账。

对于无法立即确认的结果，状态应保持 `UNCERTAIN` 或 `RECONCILIATION_REQUIRED`，而不是强行选成功或失败。

**不要用“原子事务”四个字掩盖物理提交与数据库提交无法完全同原子的事实。**

### P0-3：缺少统一时间模型

现在只强调 `sim_t`，没有解决观测链中至少五种时间：

- 物理 step 时间；
- 传感器采集时间；
- 消息到达时间；
- 证据裁决时间；
- 账本提交时间。

同一模拟时刻采集的证据，可能在不同模拟时刻才被送达。

必须明确是否采用离散事件队列，以及如何处理延迟消息、重放消息和已过期证据。

尤其要避免用 wall time 驱动证据过期、却用 sim time 评价物理稳定窗的情况。

### P0-4：月台拓扑缺乏几何和可达性验证

“复用 D_G”“floor ±3.2m 有余量”“避免盲走走廊”，这些是设计假设，不是几何审计。

月台至少需要验证：

- 卡车与建筑、货架、行车通道的实际碰撞；
- 叉车可达装卸位置；
- 载货状态下的转弯扫掠空间；
- 月台占用、车辆互斥及 AGV 交通锁的协调；
- 车辆泊入或离场不会凭空穿过其他物体。

而且静态卡车的碰撞风险不能默认 low。一个错误的静态障碍物布局完全可能让现有路线不可达。

### P0-5：你还没有严格意义上的运营数字孪生同步

现在只有：

`MuJoCo truth → CSV → Blender`

这是仿真驱动的数字场景与可视化，不等于已经与实体配送中心同步的运营数字孪生。

若没有真实设备遥测，应该明确产品级别：

- 当前：**Executable Simulation Twin / 仿真孪生**。
- 未来：具备实体遥测输入、时间同步、状态校准和偏差反馈的运营数字孪生。

这不贬低技术成果，但会避免将“仿真内部账实一致”宣传为“数字孪生与真实世界同步”。

### P1-6：缺少证据来源完整性和抗篡改设计

如果一个摄像头事件只是 JSON：

`id, type, confidence, ts, source`

那么任何能向事件总线写消息的进程，都可能伪造一个高置信度成功事件。

即使暂不建设复杂安全体系，至少应有来源身份、操作绑定、消息完整性、重放保护和持久化审计。

这是执行证据协议向工业系统迁移时不可回避的问题。

### P1-7：三维场景展示可能掩盖模型保真度不足

照片级渲染与物理可信度之间没有必然关系。

MuJoCo 1kHz 说明积分与控制更新频率，不说明摩擦、接触、托盘形变、负载分布或车辆动力学已经经过真实设备标定。

因此必须明确：

**视觉真实性、物理真实性、业务语义正确性和证据可信性是四个独立维度。**

不能用照片级宣传物理级精度，也不能用物理仿真 1kHz 证明真实工业可靠性。

|---|---|---|
| 隐式依赖项目根目录 | 从别的 repo 调用就失败 | `src/` layout，wheel 安装测试 |
| MJCF、贴图、配置没有打包 | 本地能跑，安装版缺资源 | 使用包资源机制并验证 wheel 内容 |
| 顶层 import 启动服务或 UI | core 无法无头运行 | 分离库初始化与演示入口 |
| core 反向 import `dc-twin` | 双向依赖 | 插件注册或接口注入 |
| 改造原仓导致旧仿真行为改变 | 1200 runs 无法复现 | 旧实验锁定版本与配置 |
| MuJoCo/求解器版本漂移 | 结果数值和性能改变 | 依赖版本、环境信息、回归基准 |
| Blender 与 GUI 被打入核心依赖 | 部署沉重、许可关系复杂 | 渲染独立进程与可选组件 |

Python Packaging 官方也明确说明，`src` 布局有助于防止测试意外引用源码目录而非实际安装的包。

因此打包验收不能是：

`pip install -e . && pytest`

必须额外验证：

1. 构建正式 wheel。
2. 在全新环境、不同工作目录安装。
3. 不依赖源仓库路径执行核心示例。
4. 使用安装版 wheel 运行契约测试。
5. 原有 8 车模型、事务测试和确定性基准保持兼容。

新包先使用 `0.x` 版本并显式管理契约演进，等公共 API 和兼容性边界稳定后再承诺正式稳定版本。

### 5.3 最危险的是兼容性升级悄悄改变证据语义

假设新版本改了稳定窗阈值、托盘身份关联规则，或者装车提交时刻。

这些修改可能不改变 API 签名，却改变历史实验结果。

普通语义化版本管理不够。至少要同时版本化：

`core_version`、`scenario_schema_version`、`evidence_policy_version`、`sensor_model_version`、`experiment_manifest_version`。

任何影响事务裁决结果的改动，都必须触发证据契约回归，而不是仅跑接口测试。

这里最应该保持独立的是 **Execution Evidence Protocol**，而不是卡车模型、摄像头实现或 Blender 导出器。

### 5.4 纯开源承诺基本可行，但不要说“纯开源 pip 栈”

MuJoCo 的源码采用 Apache-2.0 许可；Blender 使用 GPL 许可。二者都属于开源软件，但 Blender 不是普通 Python pip 依赖，也不能不核查许可关系就将其与全部代码混合分发。

建议把承诺改为：

**“核心运行和实验能力无需 NVIDIA 专有运行时、SDK 或许可工件；采用经过依赖与许可审计的开源组件。”**

对应验收必须有 SBOM、许可清单和无 NVIDIA GPU/驱动依赖的干净环境运行测试。不能只检查 `requirements.txt` 是否包含 NVIDIA 字符串。

## 六、§8.4 运输车队预留：确实过早，而且抽象方向不对

### 6.1 `BerthTruck / RoadTruck` 不应该是同一 Agent 的简单双态

两者在业务语义上差别很大：

| 维度 | BerthTruck | RoadTruck |
|---|---|---|
| 核心问题 | 月台装卸、货物保管交接 | 路由、在途监控、ETA、异常运输 |
| 物理空间 | 单一仓库仿真场景 | 道路网络与多个场站 |
| 时间尺度 | 秒、分钟 | 小时、天 |
| 控制模型 | 月台占用与装卸确认 | TMS/车辆远程状态 |
| 证据来源 | 装卸、位置、接触观测 | GPS、电子封签、签收、运输事件 |

这不只是对象增加一个 `RoadTruck` 子类，而是跨越新的业务限界上下文。

**v0.4 应删除 RoadTruck 类型预留，保留稳定的跨边界业务标识。**

例如：

`facility_id`、`shipment_id`、`vehicle_id`、`load_unit_id`、`handoff_id`。

未来运输车队由独立 Transport/TMS 模块接管，消费已确认的装车和发运事件即可。

### 6.2 “装车/在途/到货/卸车四态共用证据协议”也不准确

这四个可以共享事件信封格式，但不应该共享物理证明规则。

“装车成立”的判据，与“车辆到货成立”的判据根本不同。它们属于不同证据类型和责任主体。

同时，不能把装车、在途、到货、卸车混成四个互相独立的事实而没有状态转移约束。例如：

- 未发运不能确认在途；
- 未到达不能确认卸货；
- 重复到货消息不能产生第二次入库；
- 发运证据不自动授予目的地收货权限。

最小可行扩展应该是：

`Loaded → HandoffConfirmed → Departed`

到这里就停止 P0 的职责。

### 6.3 VDA 5050 不是公路运输接口

VDA 5050 面向移动机器人与主控系统的通信，不是干线卡车的 TMS 协议。

将来需要多 DC 运输网络时，应该重新审查运输状态、运输任务和设备控制模型，不应因为现在有 AGV 协议就强行复用。

**裁决：删除 RoadTruck 具体类型，保留事件化的跨场站交接边界。**

## 七、三轮自审遗漏的七个致命盲点

下面这些是我认为 v0.4 最需要补入风险登记的项目。

### P0-1：装车腿复用 `trunk`，存在语义污染

自审#1 把“装车腿复用 trunk”当成降低改动量的优化。

我不认可这个决定直接通过。

如果 `trunk` 在现有系统中代表仓内干线移动，那么其完成条件可能只是到达目标点；装车则需要确认正确托盘、正确车辆、接触/支撑、交接责任和业务提交。

**类型复用只有在动作语义及其不变量一致时才安全。**

正确方案是尽可能复用底层移动和调度能力，但明确新增装车操作的业务类型与完成规则。

否则系统可能出现：

`到达 tk 节点 → trunk 完成 → 直接出库提交`

这是对证据门控设计目标的直接破坏。

### P0-2：数据库事务与物理动作仍然存在不可消除的非原子窗口

v0.4 没有在 DC 场景里重新检查这个问题。

例如：

1. 机器人已经把托盘放上卡车。
2. 物理装车成功。
3. 系统在账本提交之前崩溃。
4. 重启后无法确认这次动作是否已经发生。

数据库事务不可能让已发生的物理动作回滚。

正确机制必须包括动作前持久化意图、操作幂等、完成后的证据裁决以及异常后的重新观测与对账。

对于无法立即确认的结果，状态应保持 `UNCERTAIN` 或 `RECONCILIATION_REQUIRED`，而不是强行选成功或失败。

**不要用“原子事务”四个字掩盖物理提交与数据库提交无法完全同原子的事实。**

### P0-3：缺少统一时间模型

现在只强调 `sim_t`，没有解决观测链中至少五种时间：

- 物理 step 时间；
- 传感器采集时间；
- 消息到达时间；
- 证据裁决时间；
- 账本提交时间。

同一模拟时刻采集的证据，可能在不同模拟时刻才被送达。

必须明确是否采用离散事件队列，以及如何处理延迟消息、重放消息和已过期证据。

尤其要避免用 wall time 驱动证据过期、却用 sim time 评价物理稳定窗的情况。

### P0-4：月台拓扑缺乏几何和可达性验证

“复用 D_G”“floor ±3.2m 有余量”“避免盲走走廊”，这些是设计假设，不是几何审计。

月台至少需要验证：

- 卡车与建筑、货架、行车通道的实际碰撞；
- 叉车可达装卸位置；
- 载货状态下的转弯扫掠空间；
- 月台占用、车辆互斥及 AGV 交通锁的协调；
- 车辆泊入或离场不会凭空穿过其他物体。

而且静态卡车的碰撞风险不能默认 low。一个错误的静态障碍物布局完全可能让现有路线不可达。

### P0-5：你还没有严格意义上的运营数字孪生同步

现在只有：

`MuJoCo truth → CSV → Blender`

这是仿真驱动的数字场景与可视化，不等于已经与实体配送中心同步的运营数字孪生。

若没有真实设备遥测，应该明确产品级别：

- 当前：**Executable Simulation Twin / 仿真孪生**。
- 未来：具备实体遥测输入、时间同步、状态校准和偏差反馈的运营数字孪生。

这不贬低技术成果，但会避免将“仿真内部账实一致”宣传为“数字孪生与真实世界同步”。

### P1-6：缺少证据来源完整性和抗篡改设计

如果一个摄像头事件只是 JSON：

`id, type, confidence, ts, source`

那么任何能向事件总线写消息的进程，都可能伪造一个高置信度成功事件。

即使暂不建设复杂安全体系，至少应有来源身份、操作绑定、消息完整性、重放保护和持久化审计。

这是执行证据协议向工业系统迁移时不可回避的问题。

### P1-7：三维场景展示可能掩盖模型保真度不足

照片级渲染与物理可信度之间没有必然关系。

MuJoCo 1kHz 说明积分与控制更新频率，不说明摩擦、接触、托盘形变、负载分布或车辆动力学已经经过真实设备标定。

因此必须明确：

**视觉真实性、物理真实性、业务语义正确性和证据可信性是四个独立维度。**

不能用照片级宣传物理级精度，也不能用物理仿真 1kHz 证明真实工业可靠性。

我建议在既有四阶段之前增加 P-1，并把所有阶段的验收对象改为可复核的交付物。
