## 0. 主轴声明 (v0.5 结构性修正)

**架构主轴 = 证据事务执行层, 不是场景。**

```
主轴 (已建成, Paper I):  PREPARED → 五门证据 → 原子提交 → 恢复对账
本设计的全部"场景能力" (月台/卡车/摄像头/what-if/渲染)
    = 主轴的演示载荷: 证明主轴在"场站物流"域的可扩展性与价值。
```

一切分期、验收、接口设计都从主轴出发回答一个问题:
**新场景要素引入的物理状态变更, 能否同样被证据裁决?**
(NVIDIA Warehouse Blueprint 只是"分层范式参考", 不是对标本体 ——
对表见 §6, 分感知范式引用与执行可信差异两节, 不再混表。)

## 1. 架构分层 (v0.5: 证据层为主轴的重排)

```
L4  Agentic 应用        证据审计 agent / what-if 扫描          (P2)
L3  场景载荷 (dc-twin)  月台/卡车/装车腿/KPI 曲面/渲染演示  ← 新增, 可替换
L2  感知微服务 (两级)   L2a 几何级检测事件 (P1) / L2b 渲染级 (P3)  ← 新增
L1.5 证据事务层 (主轴)  五门判据/原子提交/恢复对账/账本          (已有)
L1  内核 (agv-warehouse-core)  MuJoCo/调度/锁矩阵/demand      (已有)
```

- L1.5 是唯一不可替换层; L3 场景载荷通过**可扩展点**注册进主轴
  (新证据事件类型/新节点类), core 不为场景硬编码。
- 两级感知 (回应审查 4.3):
  - **L2a 几何级**: 位姿+ROI 判定产生检测事件 (P1 首版) —— 明确声明
    这是几何传感器模型, 不是视觉;
  - **L2b 渲染级**: Blender 出图 + 检测器 (P3) —— 仅演示, 结果标注
    "物理保真以 MuJoCo 模型为准, 渲染仅可视化" (回应 P1-7)。
  - **证据能力矩阵** (v0.5 新增, 随 v0.5 交付): 每种传感器 ×
    {能证明什么 / 不能证明什么 / 失效模式 / 噪声参数} 四列表。

## 2. 统一时间模型 (回应盲点 P0-3)

- 全链唯一时钟 = sim_t (MuJoCo data.time), 禁止 wall clock 进任何
  判据/日志排序。
- 每个证据帧携带三元组 **(t_event, t_observe, t_decide)**:
  事件物理发生时刻 / 传感器观测时刻 / 裁决时刻。判据窗口 (如 0.5s
  稳定窗) 一律定义在 t_event 轴; 恢复时间 = t_decide(闭合) −
  t_event(分歧首现), 语义在论文中锁定为"账本对账+重观测, 不含重新
  物理取放"。
- 验收新增: 任意证据帧必须满足 t_event ≤ t_observe ≤ t_decide
  (违反即 bug, pytest 断言)。

## 3. 分期 (载荷视角重排; 验收全部独立评分器)

**独立评分器纪律 (回应审查 3.2 自我证明)**: 所有"账实一致"判定由
**独立评分器进程**做出 —— 与 fault_ablation 的 evaluator 同模式:
评分器只读 `truth` 通道 + 账本导出, 与被测系统无共享状态、无 API
交叉; 被测系统自报的一致性仅作遥测, 不作验收。

### P0 月台+卡车载荷 (1-2 天)
- 内容: `tk:*` 节点 (交付台 D_G 延伸段, berth_depth_y 复用, 避
  x∈(-2.22,-1.10) 盲走走廊); **新增 `load` 腿类型** (自审#1 的 trunk
  复用方案被 GPT 否决: 语义污染); BerthTruck (mocap 静体+货箱 geom);
  装车证据事件 (四态之首); DemandEngine 到达时刻表。
- 验收: press.py 复用, 30min 仿真时钟; **独立评分器**断言 ≥1 卡车
  装车离场且账实三元等式成立; 全库 pytest 全绿; **非原子窗口上界
  可测**: 报告 max(t_commit − t_event_settle) 并写入验收记录
  (回应 P0-2: 窗口不可消除, 但必须可测量、受监控)。
- 接口评审前置: 账本 (truck 维度)/调度 (load 腿)/需求 (时刻表)
  三处扩展先出接口设计再实现。

### P1 两级感知之 L2a + 融合层 (2-3 天)
- 内容: 月台+关键巷道 ROI 摄像头 (L2a 几何级) → 检测事件 (schema:
  id/type/confidence/t_event/t_observe/source) → 融合层 → 门控;
  噪声 = SDG 合成参数 + 敏感性扫描 (漏检 0-30% × 误检 0-10% ×
  延迟 0-2s, 三维网格, 回应 4.4 二维不足);
  **证据能力矩阵**随代码交付。
- 分工: LiDAR 通道=避障决策侧 (不动); 摄像头事件=证据侧; 融合层
  禁读 truth (消费者分开≠信息源独立 —— 信息源独立性由构造保证:
  L2a 只从 observed 口径取数 + 自有噪声变换, 审计扩展覆盖)。
- 验收 (**Pareto 联合可行域**, 回应 3.3 三约束矛盾): 逐噪声网格点
  报 (unsafe, FRR, 吞吐损失) 三元组, 画 Pareto 前沿; 签字门槛 =
  前沿存在非支配点满足 unsafe=0 ∧ FRR≤5%; 吞吐损失作为前坐标报告
  而非硬门槛。独立评分器同 P0。

### P2 What-if + KPI (1-2 天)
- 内容: 场景矩阵 (6/8/10 车 × 4/6 月台 × 1/2/3 峰值) × 30 seed;
  **定位修正 (回应 3.4)**: P2 是"场景扫描器" (scenario sweeper),
  优化器 (在扫描曲面上做决策) 是 P2.5 候选, 不在本期验收。
- KPI & Metrics / Latency 章节 (对齐 Blueprint Profile 惯例):
  吞吐/利用率/账实一致率/门控时延分位数 (p50/p95/p99, t_decide−
  t_observe 轴)。
- 验收: 3×3×1 摸底定计算量后全矩阵; 曲面报告 + 时延分位表。

### P3 渲染演示 (1 天)
- L2b 渲染级感知 (演示用) + 60-90s 成片; 保真度声明入片头。

## 11. v0.5.1 冻结修订 (GPT 第五轮 CONDITIONAL PASS, 2026-10-13)

裁决: 架构方向批准; P0-2 命题定位正式接受 (非原子窗口是研究对象,
不要求消除; **未决窗口可监控、异常可恢复、风险不被错误提交掩盖**
为强制验收)。五项冻结条件已并入:

### C1 时间模型 (BLOCKER·P0 前)
运行时证据帧字段改为 **t_capture / t_ingest / t_decide** (+可选
estimated_event_time, 带不确定性标注); **t_event(真值) 移出运行时
证据**, 只存在于独立评分器 (truth_event_time/truth_settle_time/
truth_state/durable_commit_time)。物理稳定窗由观测序列+观测有效期
判定。时钟口径: sim_t=业务语义与确定性调度; wall time 仅监控
(watchdog/资源), 两时钟域不混算同一指标; 跨域单调性断言仅限同时钟。
验收: 延迟/乱序/重复/过期/跨重启五类消息测试, 门控不依赖评分器
独有真值时间。

### C2 独立评分器 Oracle 独立契约 (BLOCKER·P0 前)
评分器: 只读独立导出的真值轨迹 + 持久化账本快照/事件日志; 不调用
被测系统业务判定函数; 按 pallet_id+location+custody+operation_id
核对归属与事务; 快照边界区分短暂未决 vs 持久账实错误; 记录输入
哈希/core 版本/规则版本/run_id。
**六类负向验收 (新增)**: 未装车伪造成功 / 装错卡车 / 提交前崩溃 /
提交后 ACK 丢失 / 重复事件 / 未结清货物离场 —— 评分器必须识别;
正确但未闭合事务必须判"待恢复"而非"完成/丢失"。

### C3 Pareto 方法论 (BLOCKER·P1 前)
漏检/误检/延迟是**环境条件不是策略变量**: 固定噪声条件, 在该条件
下扫**可控策略** (重观测次数/融合阈值/证据等待预算), 按噪声条件
分层各成 Pareto 前沿, 比较跨条件鲁棒性。签字门槛恢复吞吐约束:
unsafe=0 ∧ FRR≤5% ∧ **吞吐损失≤10%** 同时满足 (防"挂起换指标")。

### C4 两级感知真值身份 (BLOCKER·P1 前)
L2a 禁止使用带真值身份的 observed 通道 —— 观测接口按"摄像头只能
看到相机坐标系投影+检测置信度"重新定义; 注入**共同原因故障**
(同一物理事件同时污染 LiDAR 与摄像头) 验证门控不因双源一致而误判。

### C5 契约回归门 (BLOCKER·CI)
从"冻结历史数字回归"改为**语义+统计回归**: 断言不变量 (unsafe=0
于无注入、账实最终一致、恢复语义) + 统计等价检验 (Wilson 区间重叠),
历史数字仅作参考线。

## 13. 优先级重排 (用户定向 2026-10-13): 产线优先

**L3 载荷优先级: line-feed (产线供料) > dc (月台/卡车)。**

### line-feed P0' 载荷 (dc-twin `dc_twin/line/`)

```
仓库(已有) → AGV 供料(load/pick 腿) → 线边库 L-B1..B3 (新增, 2 层小架)
  → 看板拉料 (takt 驱动 pull 需求, DemandEngine 扩展)
  → 产线工位 ST-PRESS (新增, MuJoCo 机构: 冲压头 actuator + 工件夹具)
  → 上料证据事件 + 工序完成证据事件 (力剖面) → 成品托盘 → 出库
```

- **工位证据门控**: 上料=工件入夹具到位+夹紧确认 (L2a 几何级);
  工序完成=冲压头力剖面达标+节拍窗内 (力证据, MuJoCo 强项)。
- **PLC**: 复用 B4 `_PlcStub` 模式 (状态字 ACK), 不读真值。
- **独立评分器**: 产量对账 (工位物理完成数 vs 账本提交数) + 物料追溯
  (pallet_id→工位 operation_id), 同 C2 契约。
- **六负向用例**: 空料上料 / 伪造工序完成 / 重复投料 / 未夹紧动作 /
  节拍超时未报 / 错工位投料。
- 验收: 30min 仿真时钟, takt 拉料连续运转, 零停线 (线边库不空),
  评分器产量对账一致, 全库+dc-twin 测试全绿。

## 14. 场景对标: 可口可乐装瓶体系 (英伟达×可口可乐全景分析, 2026-10-13)

以"英伟达×可口可乐"全景分析为参照系, line-feed 载荷对标**真实装瓶厂**
场景栈。核心差异不变: 分析中所有系统 (Sight Machine 孪生/Krones CFD/
Intenseye/SAI) 都是**感知-分析-告警**层, 无一做"物理证据→账本提交
裁决" —— 我们的证据事务层是这套体系的缺失层。

### 14.2 语义修订 (LineP0 执行中, 只改名与叙事, 不 destabilize)

- ST-PRESS 叙事定位: "压盖/冲压类工位的力学抽象" (真实装瓶线的
  压盖工序: 曲线咬合+压线力判定, 与我们力剖面证据同构)。
- 术语: 场景叙事从 "DC 配送中心" 扩为 **"装瓶厂+配送网络"**;

## 17. 框架定位: ESR — Evidence-Simulation-Ready (超越 SimReady 的开源 agentic 仿真框架)

用户北极星 (2026-10-13): 用最新开源组件 + agentic 技术, 构建设计和
思路上**超越 NVIDIA SimReady** 的框架。

### 17.1 SimReady 现状 (2026, AOUSD 治理)

SimReady = OpenUSD 资产内容规范: USDPhysics 物理属性 / 语义标签 /
材质 / dense captions / **非视觉传感器属性** / 多运行时规格
(simready-foundation, 解决跨物理引擎资产易碎问题)。
它解决的是: "资产丢进仿真就能用"。它**不解决**: 资产动作的可信
执行、资产间的事务语义、agentic 组合的可验证性。

### 17.2 ESR = SimReady 超集 (四层资产-运行时框架)

| 层 | SimReady | ESR (本框架) |
|---|---|---|
| L-资产几何/物理/语义 | USD (AOUSD) | GLB+manifest 核心; **OpenUSD 导出适配器** (interop 不设墙) |
| L+1 **证据契约** ★ | 无 | 资产自带 evidence manifest: 哪些传感器组合能证明哪些状态转移、提交语义、恢复行为、非原子窗口上界 |
| L+2 **技能接口** ★ | 无 | MCP tool 面: 每资产/工位暴露 agent 可调用技能 (前置条件→执行→证据→后置条件), Voyager 式技能库注册 |
| L+3 **可验证性** | 无 | 资产/场景随附消融-评估 harness (B0-B4 基线), 指标预注册 |
| 运行时 | 引擎无关 spec | 证据事务内核 (MuJoCo, 已建成) |

★ = ESR 新增层。一句话: **SimReady 让资产"能仿真", ESR 让资产
"能被信任地执行、被 agent 操作、被独立验证"**。

### 17.3 agentic 技术栈 (最新开源组件选型)

- **MCP (Model Context Protocol)**: 资产技能面统一暴露为 MCP tools
  (场景组装/工位操作/对账查询), 任意 LLM 客户端可驱动 —— 对标并
  超越 Warehouse Blueprint 的 API Gateway/MCP。
- **LLM 组合场景**: 自然语言→场景装配 (对标 USD Search/Code NIM 的
  开源实现: 本地 embedding 检索资产生命册 + 代码生成)。
- **Agent 事件消费**: 证据审计 agent / 瓶颈分析 agent 消费事件 ring
  (Warehouse Blueprint Agents 层的开源对应)。
- 渲染: three.js/GLB (实时) + Blender Cycles (离线照片级)。

### 17.4 落地路径 (现有资产 → ESR)

1. dc-twin P0' (已建) = ESR 运行时+第一个场景的雏形;
2. 把 line registry/证据事件/技能面重构为 ESR manifest+MCP 规范
   (P0'.5 后);
3. 发布 ESR 规范 v0.1 (assets/evidence-contract/skill-interface
   三份 spec) + dc-twin 作为参考实现;
4. 学术叙事: Paper I 为主轴论文, ESR 为框架论文 (Paper III 候选)。

## 18. ESR 本质区别: 自进化闭环 (SimReady 没有智商)

用户定调 (2026-10-13): 实现和 SimReady 类似的场景, 但核心依靠
**agentic 自我知识积累与进化** —— SimReady 资产是委员会写死的静态
内容, 没有智商; ESR 的场景/资产**随运行经验生长**。

### 18.1 自进化闭环 (ESR-Loop, 五拍)

```
① 运行   ② 经验结晶   ③ 知识沉淀   ④ 场景进化   ⑤ 消融验证
sim 连续 → 事件/故障/   → 技能库+证据  → 注册表新类型/  → 30-seed
运转     停机/对账分歧   契约自动起草   证据契约自动生成  契约回归门
   ↑______________________________________________________|
```

### 18.2 每一拍在本仓库的实锤 (不是愿景)

| 拍 | 已有实证 |
|---|---|
| ① 运行 | 30min×3 压测 + 24h 架构 + 1200 runs |
| ② 经验结晶 | DetFix: 16 runs 把 6 层故障链炼成三修复; jam 探针定位路由几何 |
| ③ 知识沉淀 | robot_skills (Voyager 式技能库: 前置条件→执行→证据→后置条件); 故障矩阵 22 场景全部来自真实事故 |
| ④ 场景进化 | core 扩展点注册表 (节点源/腿类型/事件类型/到达源) — 新场景类型 agent 可注册, 不碰主路径; ESR manifest 起草 |
| ⑤ 消融验证 | fault_ablation 1200 runs 契约回归门; B4 强基线来自外部评审经验结晶 |

SimReady 的"规格"由委员会发布后冻结; ESR 的规格由**运行经验持续
改写**, 每一次进化都要过 ⑤ 的消融门 —— 进化不靠信仰, 靠消融。

### 18.3 ESR-Loop 形式化 (下一步)

- `esr/` 包: Loop 编排器 (②→③④⑤ 的 agent 工作流, MCP 工具面);
- 技能结晶格式: incident → {根因假设, 修复动作, 回归用例, 证据契约
  修订} 四件套 (DetFix 交付物即第一个样本);
- 场景进化门: 新注册类型必须附 (证据契约草案 + 消融子集) 方可入册。
